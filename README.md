# Crowd3D：众包打卡照片 → 地标三维模型（原型）

不同的用户在著名建筑前打卡，从不同角度上传照片。系统自动判断每张照片是从建筑的哪一侧、朝哪个方向拍的。照片还不够时，先重建能拍到的那一面（**立面模型**）。照片覆盖了大部分方向后，再重建整栋建筑（**全景模型**）。模型以地标中心为原点，单位是米，北向对齐。

在点云之上，原型还能生成一个**风格化的"玩具"模型**（GLB）。它走"结构优先"的路线，参照 Hover 的做法：

- **框架先取自地图。** OpenStreetMap 的 Simple 3D Buildings 分件（`building:part`）变成参数化积木。每块积木带一个屋顶原语（平顶、单坡、双坡、四坡、攒尖、穹顶、洋葱顶……），每个参数都记下来源。
- **照片按规则修改地图上的值。** 证据有三路：天空轮廓线、SfM 点、三维直线。
  - 至少两路一致时自动采用（D15）；改高度时还要读到这块积木自己的屋顶（D27）。
  - 照片量出立面的凹凸（D24）。
  - 证据足够强时把 OSM 的高度往上纠正、加上倾斜、给缺高度的部分补出体块（D25）；每处纠正都可以撤销。其中倾斜（D25-T）的代码在仓库里，但没有接进任何入口，见下面"现状"。
- **模型一律是素模**（浅冷灰加淡斜纹）。决定 D29（产品负责人，2026-11-03）放弃了给模型上照片颜色，上色代码已删。照片只用来把模型放准，并在配准通过时核验、修正形状（上一条）。画风可以整套替换素模色、描边和光影。

这是一个只用 CPU 的最小原型。后端是 Python（FastAPI + SQLite + pycolmap），前端是不需要构建的原生 JS 页面。另带一个能生成"真值"的合成数据生成器，用于测试和演示。

> **这是原型，网站没有上线，现在所有的照片都是测试照片。** 它不是测绘工具，也不做照片级的三维重建：点云是稀疏的，风格化模型是 OSM 分件搭的素模（"玩具"，不是真实记录），照片只用来把模型放准、在放得准的时候核对形状。什么能用、什么不行，见下面的[现状](#现状什么能用什么不行)。

## 工作原理

```
上传 ─▶ 读 EXIF ─▶ 校验 ─▶ 入库（扇区）─▶ 覆盖规划 ─▶ 重建作业（COLMAP）─▶ 地理配准 ─▶ 发布质量门 ─▶ PLY + 元数据 ─▶ 网页
                                                                                          │
                               （风格化作业，在子进程里）OSM 分件框架 + 照片证据 + 风格化 ◀─┘ ─▶ GLB ─▶ 风格化查看器
```

1. **上传**：先登记昵称、同意用户协议（只要一次），再传照片。每张照片读 EXIF、过校验：要有 GPS、在地标的打卡半径内、不背对建筑、建筑是照片的主体、不太小、不太糊、不重复。不合格的逐张给出原因。
2. **扇区**：地标四周分成 8 个扇区，照片归入拍摄者所在的那一面。
3. **规划**：一面有 4 张合格照片就排一个**立面作业**；总数到 24 张、够 6 面时排**全景作业**；照片再多，就按增长量重建。
4. **重建**：COLMAP（只用 CPU）做 SfM，特征和匹配有地标级的缓存；小照片集换种子建几次，留下最可信的一个。
5. **地理配准**：用照片的 GPS 和标成真北的罗盘读数，把模型放进以地标中心为原点的坐标系（米，北向对齐），并记下每个分量的不确定度。
6. **发布质量门**：只和产品本来就知道的东西比（照片的 GPS 和罗盘、地标中心）。没过门的模型不发布，之前的版本继续显示。
7. **输出**：点云（PLY）和元数据。通过校验、没撤回、确定了位置和朝向的照片，连同取整到 1 米、1° 的拍摄位置公开。
8. **风格化**（地标有 OSM 分件快照时）：分件搭成参数化积木，照片证据只在配准门通过时用来核对和修正形状，输出素模 GLB。

每一步的规则、门槛和例外见 [docs/PIPELINE.md](docs/PIPELINE.md)。

## 快速开始

需要 Python ≥ 3.11（开发时用 3.13）。运行 Web 测试还需要 Node ≥ 22（开发时用 v22），可选：测试用到了 `mock.timers` 的 Date 模拟和 `node --test` 的通配符，旧版本跑不了。

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt -c requirements-lock.txt

python -m pytest -q -m "not slow"        # 快速测试，不需要真实照片；单进程约 5 分钟，以这个写法为准
python -m pytest -q -m "not slow" -n 4   # 同一批测试分 4 个进程跑，约 1.5 分钟
python -m pytest -q -m slow              # 慢测试（真实 COLMAP、端到端验收、风格化作业端到端、13 个地标的素模回归）；不要加 -n
python -m ruff check .                   # 代码检查，规则在 pyproject.toml
```

依赖分四个文件，每个包都钉了版本（`tests/test_tooling.py` 会核对代码里的导入和这些文件是否一致）：

| 文件 | 用途 |
|---|---|
| `requirements.txt` | 只运行服务：`crowd3d/` 直接导入的第三方包 |
| `requirements-eval.txt` | 再加上 `scripts/` 和评测要用的（httpx、pyarrow） |
| `requirements-dev.txt` | 再加上测试和检查要用的（pytest、pytest-xdist、ruff）；开发和 CI 装这个 |
| `requirements-lock.txt` | 三套测试最近一次全部通过时那个干净环境的 `pip freeze`，连间接依赖一起钉住；安装时当约束文件用（`-c`） |

启动服务，然后运行演示：

```bash
python -m crowd3d.api --seed-demo   # http://127.0.0.1:8000 ，创建地标 demo-building
python scripts/demo.py              # 另开一个终端
```

`demo.py` 会生成合成照片，然后按一个故事分阶段上传。整个过程在 4 核 CPU 上约 1 分钟：

1. 游客1 在北侧拍了 4 张 → 生成北立面模型；
2. 更多游客拍了东北、东、东南、南 → 每面各生成一个立面模型；
3. 一位游客补齐了剩下几面 → 生成剩下的立面模型和全景模型（32 张照片）；
4. 几张不合格的照片 → 逐张显示拒绝原因。

终端里会打印文字版罗盘、作业状态和模型质量。最后给出查看地址，例如 `http://127.0.0.1:8000/landmark.html?id=demo-building`。在浏览器里可以看到罗盘、共同完成者、作业列表、模型列表和 three.js 点云查看器。首页 `http://127.0.0.1:8000/` 是地图和地标列表。

- **服务要在仓库的检出目录里运行**：包不能安装，网页和默认的地标目录都取自检出目录（[docs/CONFIG.md](docs/CONFIG.md#服务要在仓库的检出目录里运行)）。
- 数据目录、假重建器（调界面用）、`public_id.salt` 的备份、演示脚本的选项、风格化脚本和查看器的用法，见 [docs/USAGE.md](docs/USAGE.md)；每个配置项见 [docs/CONFIG.md](docs/CONFIG.md)；HTTP 接口见 [docs/API.md](docs/API.md)。

## 测试

三套测试，命令在上面的代码块里：

- **快速测试**（一千四百多个，不需要真实照片）：`python -m pytest -q -m "not slow"`，加 `-n 4` 并行；直接运行 `pytest` 也可以。
- **慢测试**（40 个，真实 COLMAP 和 13 个地标的素模回归，约 10 分钟）：`python -m pytest -q -m slow`，不要并行。
- **网页的 node 测试**（211 个）：`node --test 'web/tests/*.test.mjs'`。

每次 push，CI 跑代码检查、快速测试和 node 测试。只跑一部分测试的标记、每一套测什么、已知的缺口，见 [docs/TESTING.md](docs/TESTING.md)。在冻结测试集（10 栋真实建筑的照片）上跑完整链路的基准不在 pytest 里，见 [docs/BENCHMARK.md](docs/BENCHMARK.md)。

## 现状：什么能用，什么不行

下面的数字来自冻结测试集上的基准：10 栋著名建筑、1,045 张自带 GPS 的 Wikimedia Commons 照片，分成开发集五栋和留出集五栋。取的是 D34 的两次全新运行（默认配置，各重复两次，数是两次的中位数），出处是 [docs/BENCHMARK.md](docs/BENCHMARK.md#614-d34-的全新运行第四个开关和地理配准默认值的全新确认) 6.14 节。

**能用的**

- **整条链路接进了服务和网页**：登记、上传、校验、重建、地理配准、质量门、发布、撤回。合成数据上端到端通过（慢测试）。
- **有 OSM 分件快照的地标（目录里 13 个），每个发布的模型自动出一个素模 GLB**。查看器里能点积木看来源、看公开的拍摄位置、把照片和素模放在一起对照。
- **真实照片上，立面模型发布得出来**：开发集五栋每次运行发布 66 个模型，19 个立面有模型；留出集五栋发布 26.5 个模型，9 个立面有模型。

| 建筑 | 划分 | 收下的照片 | 发布的模型 | 有模型的立面 | 显示的拍摄位置 | 其中对的 | 其中错的 |
|---|---|---|---|---|---|---|---|
| 佛罗伦萨洗礼堂 | 开发 | 51 | 6 | 5 | 39 | 12 | 5 |
| 亚琛大教堂 | 开发 | 75 | 3 | 2 | 40 | 1 | 0 |
| 勃兰登堡门 | 开发 | 136 | 28 | 4 | 84 | 56.5 | 9.5 |
| 比萨斜塔 | 开发 | 115 | 10.5 | 3 | 83.5 | 60 | 11.5 |
| 德累斯顿圣母教堂 | 开发 | 83 | 18.5 | 5 | 63.5 | 17 | 42.5 |
| 圣家堂 | 留出 | 128 | 16 | 3 | 52 | 41.5 | 4.5 |
| 匈牙利国会大厦 | 留出 | 86 | 4.5 | 3 | 45 | 2 | 12 |
| 林肯纪念堂 | 留出 | 58 | 2 | 1 | 31 | 5 | 15 |
| 印度门 | 留出 | 65 | 4 | 2 | 48 | 16 | 1 |
| 悉尼歌剧院 | 留出 | 62 | 0 | 0 | 10 | — | — |

"对"指离参考位姿 10 米以内、朝向差 15° 以内；没有参考位姿的照片不算对也不算错（悉尼歌剧院没有参考位姿）。逐栋的数在结果文件 `eval/results/commons-ten-v1/d34-fresh/d34-dev-doff.json` 和 `eval/results/commons-ten-v1/d34-test.json` 里。

**不行的**

- **显示的拍摄位置约三分之一是错的。** 能和参考比的里面，留出集五栋对 64.5 个、错 32.5 个，开发集五栋对 146.5 个、错 68.5 个。
- **有的建筑什么都发布不了，有的发布了但多数是错的。** 悉尼歌剧院一个模型都没有。匈牙利国会大厦、林肯纪念堂、圣母教堂能和参考比的位置里，错的比对的多；亚琛只有 1 个位置能和参考比。
- **尺度不准。** 留出集能和参考比的 29 个模型里，6 个的尺度偏差超过 35%，D34 的改动没有让它变小。没能用 GPS 配准的模型，尺度是粗估的，在真实建筑上常偏大 1.5–2.4 倍（[7.7 节](docs/BENCHMARK.md#77-照片位姿photo_pose_)）。
- **全景模型基本发布不了。** 这两次全新运行里，十栋一个全景模型都没有；更早的一次运行里，只有比萨斜塔在两次重复里出过一次。
- **照片证据进不了真实的众包模型。** 风格化的配准门要求相机位置误差 ≤ 1.5 m，真实众包模型没有一个过得了，所以产品给出的都是 OSM 分件的素模，没有照片量出的数字。模型也不上色（D29）。
- **只测了十栋建筑，阈值是样本内的。** 留出的五栋对后来的决定也已经不是没看过的数据。
- **上线前还缺**：账号和限流、内容审核、下架照片的运维命令、法律审核过的用户协议（现在是草案）；D32 的一次性迁移要删掉。
- **有几个结果从仓库复现不了。** 例如比萨斜塔的倾斜（D25-T）是不在仓库里的驱动脚本量的，仓库里没有入口能跑到这部分代码（[docs/decisions/README.md](docs/decisions/README.md#数字出处和-scratch-路径)）。

完整的局限清单和下一步见 [docs/STATUS.md](docs/STATUS.md)。
