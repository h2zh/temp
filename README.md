# Crowd3D：众包打卡照片 → 地标三维模型（原型）

不同的用户在著名建筑前打卡，从不同角度上传照片。系统自动判断每张照片是从建筑的哪一侧、朝哪个方向拍的。照片还不够时，先重建能拍到的那一面（**立面模型**）。照片覆盖了大部分方向后，再重建整栋建筑（**全景模型**）。模型以地标中心为原点，单位是米，北向对齐。

在点云之上，原型还能生成一个**风格化的"玩具"模型**（GLB）。它走"结构优先"的路线，参照 Hover 的做法：

- **框架先取自地图。** OpenStreetMap 的 Simple 3D Buildings 分件（`building:part`）变成参数化积木。每块积木带一个屋顶原语（平顶、单坡、双坡、四坡、攒尖、穹顶、洋葱顶……），每个参数都记下来源。
- **照片按规则修改地图上的值。** 证据有三路：天空轮廓线、SfM 点、三维直线。
  - 至少两路一致时自动采用（D15）；改高度时还要读到这块积木自己的屋顶（D27）。
  - 照片量出立面的凹凸（D24）。
  - 证据足够强时把 OSM 的高度往上纠正、加上倾斜、给缺高度的部分补出体块（D25）；每处纠正都可以撤销。
- **模型一律是素模**（浅冷灰加淡斜纹）。决定 D29（产品负责人，2026-11-03）放弃了给模型上照片颜色，上色代码已删。照片只用来把模型放准，并在配准通过时核验、修正形状（上一条）。画风可以整套替换素模色、描边和光影。

这是一个只用 CPU 的最小原型。后端是 Python（FastAPI + SQLite + pycolmap），前端是不需要构建的原生 JS 页面。另带一个能生成"真值"的合成数据生成器，用于测试和演示。

## 快速开始

需要 Python ≥ 3.11（开发时用 3.13）。运行 Web 测试还需要 Node ≥ 22（开发时用 v22），可选：测试用到了 `mock.timers` 的 Date 模拟和 `node --test` 的通配符，旧版本跑不了。

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt

python -m pytest -q -m "not slow"   # 快速测试，不需要真实照片
python -m pytest -q                 # 加上慢测试（真实 COLMAP、端到端验收、风格化作业端到端、13 个地标的素模回归）
```

启动服务，然后运行演示：

```bash
python -m crowd3d.api --seed-demo   # http://127.0.0.1:8000 ，创建地标 demo-building
python scripts/demo.py              # 另开一个终端
```

`demo.py` 会生成合成照片，然后按一个故事分阶段上传。整个过程在 4 核 CPU 上约 1 分钟：

1. 游客1 在北侧拍了 4 张 → 生成北立面模型；
2. 更多游客拍了东北、东、东南、南 → 每面各生成一个立面模型；
3. 一位游客补齐了剩下几面 → 生成剩下的立面模型和全景模型（32 张照片）；
4. 几张不合格的照片 → 逐张显示拒绝原因。

终端里会打印文字版罗盘、作业状态和模型质量。最后给出查看地址，例如 `http://127.0.0.1:8000/landmark.html?id=demo-building`。在浏览器里可以看到罗盘、共同完成者、作业列表、模型列表和 three.js 点云查看器。首页 `http://127.0.0.1:8000/` 是地图和地标列表。

常用参数：

- `python -m crowd3d.api`：`--data-dir DIR`（默认 `./data` 或 `$CROWD3D_DATA_DIR`）、`--reconstructor fake`（不跑 COLMAP，秒出假模型，适合调界面）、`--host`、`--port`。
  数据目录里的 `public_id.salt` 是公开 id 和撤回凭证的密钥，要和数据库一起备份，拷贝数据目录时也要一起拷。密钥和数据库对不上时（设了或改了 `$CROWD3D_PUBLIC_ID_SALT`、文件被删或被换），只要还有照片公开着，服务就拒绝启动，免得已经发出的撤回凭证全部失效、这些照片却继续公开。D32 起每张通过、没撤回的照片都算同意公开，所以有照片的数据目录基本都会拒绝。恢复原来的密钥即可；密钥确实丢了，就运行 `python -m crowd3d.consent forget-lost-salt --data-dir DIR`，它撤回所有照片的公开（位置和照片本身），再改用现在的密钥（D30）。
- `python scripts/demo.py`：`--users N`（参与的游客数）、`--size 800x600`（照片越大越慢，默认 640x480）、`--seed 1`（换一组照片；同一组照片重复上传会被判为重复）、`--landmark ID`（新建或使用另一个地标）、`--server URL`、`--photos DIR`。演示的每位游客先登记一次、同意用户协议（D33；D32 时是每次上传都同意），再用登记的凭证上传，所以通过的照片在下一次建模确定了位置和朝向后公开。
- 自己生成照片，再从网页手动上传：`python -m crowd3d.synthetic --out /tmp/photos --size 640x480`。照片的 EXIF 带 GPS 和指南针朝向，目录里有 `manifest.json` 记录真值。

> 网页用的 Leaflet 和 three.js 由服务自己提供（`web/vendor/`，D34），不依赖 CDN。只有首页的地图底图来自 OSM 的公共瓦片：浏览器不能访问外网时地图是空的，别的功能照常。

### 风格化模型

**服务会自动生成。** 地标满足下面三条时，每发布一个 COLMAP 模型，作业系统就排一个风格化作业：
- 地标目录（`Settings.structure_catalog`，默认 `eval/landmarks.json`）里有它的 OSM 分件快照和轮廓。目录里的 13 个地标都有。
- 地标 id 等于目录里的 slug（例如 `florence-baptistery`），或者在 `Settings.structure_bindings` 里绑定了 slug。
- 目录里的中心在地标的打卡半径内。

GLB 放在 PLY 旁边。地标页的模型列表里会出现"风格化模型 · 素模（照片未对齐）"或"风格化模型 · 素模（照片已对齐）"的链接（两种都是素模，区别是照片的配准有没有被接受），生成中显示"风格化生成中"。演示地标 `demo-building` 不在目录里，`--reconstructor fake` 也不写稀疏地图，所以演示不会生成 GLB。

**也可以用脚本处理单个模型。** 需要两样输入：
- 一个已重建的作业，或者 MegaDepth-X 格式的参考场景（`--scene DIR`）。作业目录默认会被清理。要保留，启动服务前设环境变量 `CROWD3D_KEEP_WORK_DIRS=1`（D34；也可以在代码里用 `Settings(keep_work_dirs=True)`），没有命令行参数。基准（`scripts/benchmark.py`）默认会保留作业目录。
- 地标在 `eval/landmarks.json` 里的条目：坐标、OSM 轮廓文件和分件快照（`osm_parts`）。外轮廓拉伸时，高度标签来自轮廓 GeoJSON；结构优先时，来自分件快照里每个分件的标签。条目里只有 Wikidata 编号，脚本用不到 Wikidata 的高度。

输出必须写到仓库外（或被 git 忽略的 `data/`）：GLB 里没有照片像素，但摆放位置和照片量出的数字来自有许可要求的照片，照片缓存里还有照片衍生的天空掩码和线段：

```bash
python scripts/stylize_model.py --job-dir data/work/<作业> --meta data/models/<地标>/<模型>.json \
    --landmark florence-baptistery --out data/stylized
```

地标有分件快照时（目录的 `osm_parts`，或用 `--osm-parts FILE` 指定别的快照），脚本默认走结构流水线 `crowd3d.structure_pipeline`。它和服务的风格化作业是同一个入口：
- OSM 分件做体块；
- 照片的配准被接受时，用 A+R 天空掩码、SfM 点和三维直线做 D15 判定；
- D25 按 `--d25` 执行：`auto`（默认）只在有两种可商用天空掩码时跑，所以今天不跑；`survey` 只量不改；`off` 不跑。

`--no-structure` 退回外轮廓拉伸。摘要 JSON 的 `structure_run` 写明跑了什么、没跑的原因。天空掩码和线段缓存在 `<out>/cache`。

crowd3d 只认 A+R 一种天空掩码（`structure_pipeline.PRODUCT_MASKS`），别的掩码名一律拒绝，没有绕过的开关。研究用的掩码（例如 Dm+R）只在仓库外的研究脚本里用，因为它们的许可没有确认可以商用（见 [docs/REVIEW_ADOPTION.md](docs/REVIEW_ADOPTION.md) 第 1 节）。

`--snap-from <旧摘要或 GLB>` 复用旧版本的吸附，重新发布时模型不漂移。流水线模型（`--job-dir`）要先通过现在的吸附门重新核对；参考场景（`--scene`）存下的吸附原样复用。

输出包括 GLB、摘要 JSON 和调试用的俯视草图（`<slug>-topdown.png`，标出拍到的墙）；有 D25 纠正时另有一份 OSM 修正建议（`<slug>-osm_fix_suggestions.json`）。

查看方法：
- 查看器 `web/stylized.html?model=<GLB 的地址>&theme=<画风>` 只接受同源地址或相对路径。可选画风是 `default`、`storybook`、`dusk`、`blueprint`，画风只换素模色、描边和光影。D29 之前写的、带照片颜色的旧 GLB 也显示成素模。
- 加上 `&poses=<地标的 /poses 地址>`（同源，地标页的风格化链接自动带上）会在素模上画出公开的照片在哪儿拍、朝哪拍（D30，`web/photoposes.js`）：模型重建的照片画成视锥（橙色，要有测出的高度、俯仰、横滚和视角，否则只在地上画朝向扇形），手机 GPS + 罗盘的照片在地上画朝向扇形（黄色，标"手机 GPS + 罗盘（未经模型核对）"）。2σ 范围超过 10 米的照片一律在地上画出范围圆；点选一张看卡片（来源、离中心的位置、朝向、2σ 范围、这个来源实测落在范围内的比例、取整说明）。
- 卡片上的"从这张照片的角度看"（D32，`web/compare.js`）把照片和从照片位姿看到的素模放在一起：宽屏并排、窄屏上下，"叠加"模式把照片盖在素模上、用滑块调浓淡。只有测出了高度、俯仰、横滚和视角的照片才能对照；EXIF 照片和缺测量值的照片只有"看照片"，单独显示照片并写明为什么不能对照。照片来自 `/poses/<公开 id>/photo`。
- 其余参数：`photos=0`（先不显示）、`photo=<公开 id>`（选中）、`view=<公开 id>`（打开对照或"看照片"）、`cmp=pair|overlay`（并排 / 叠加）、`opacity=<0–100>`（叠加时照片的浓淡）、`err=1`（画出所有照片的范围）、`cluster=0`、`fit=model`。
- 服务生成的 GLB 在 `/files/models/<地标>/<模型>.glb`，地标页直接链过去。
- 脚本写出的 GLB 服务不提供（`/files/models` 只读 `data/models`）。可以在仓库根目录起一个静态服务器（例如 `python -m http.server`），再打开 `/web/stylized.html?model=/data/stylized/florence-baptistery.glb`。

## 工作原理

```
上传 ─▶ 读 EXIF ─▶ 校验 ─▶ 入库（扇区）─▶ 覆盖规划 ─▶ 重建作业（COLMAP）─▶ 地理配准 ─▶ 发布质量门 ─▶ PLY + 元数据 ─▶ 网页
                                                                                          │
                               （风格化作业，在子进程里）OSM 分件框架 + 照片证据 + 风格化 ◀─┘ ─▶ GLB ─▶ 风格化查看器
```

### 点云链路（已接进服务）

1. **读 EXIF**（`exif.py`）：GPS、指南针朝向（`GPSImgDirection`）、焦距、机型、拍摄时间。
2. **校验**（`validation.py`）：所有不通过的原因一起返回，不会遇到第一个就停。拒绝码有：
   - `no_exif`、`no_gps`、`no_landmark`、`too_far`（超出地标半径）
   - `facing_away`（指南针朝向偏离"相机→地标"方向超过 60°）
   - `not_subject`（D31：相机离建筑的 OSM 主轮廓超过 50 m，并且估算建筑占画面不到 1/3。占比由 GPS 位置、OSM 分件和焦距算出，不看像素、不用罗盘；焦距缺失或不合理时按 28 mm 算。见 `subject.py`）
   - `too_small`（短边 < 480 px）
   - `too_blurry`（拉普拉斯方差，按 800 px 归一化）
   - `duplicate`（dHash 汉明距离 ≤ 4）
   - `unreadable_image`
   - 另外，`ingest.py` 在两种情况下给出 `too_large`，并且只返回这一个码：文件超过 25 MB；或者超过 5000 万像素、又不是能缩小解码的 JPEG（PNG、WebP，以及渐进式、分量分开扫描、无损或算术编码的 JPEG 都受这个上限限制，D34）。文件头里的东西比相机写的多得多的图按 `unreadable_image` 拒绝，Pillow 不打开它，也不解码（D34）：JPEG 的 EXIF 超过 64 KiB（一个段能装下的量，相机只写一个段），PNG 或 WebP 的 EXIF 块超过 4 MiB，JPEG 在第一次扫描之前超过 1000 个段或 64 KiB 的杂字节，PNG 超过 1000 个非像素块、65,536 个像素块或 16 个压缩块，WebP 超过 1000 个块；完整的表在 [docs/decisions/D34-review-fixes.md](docs/decisions/D34-review-fixes.md)。
   - 警告码不会导致拒绝：`no_heading`（没有指南针，无法检查朝向）、`magnetic_heading`（朝向是磁北，没有做磁偏角修正）、`subject_unchecked`（地标没有绑定 OSM 轮廓，或者分件快照读不出来，没有检查建筑是不是照片主体）。
   - 每张照片存下 `outline_distance_m` 和 `subject_share`，以后改阈值可以重判；已经收下的照片不回头重判。
3. **扇区**（`coverage.py`）：地标四周分成 8 个罗盘扇区（N、NE……NW）。照片归入"地标中心→拍摄者"方位所在的扇区，也就是拍摄者看到的那一面。
4. **覆盖规划**（`coverage.plan_jobs`，纯函数）：
   - 某个扇区有 ≥ 4 张合格照片时，触发**立面作业**，输入是该扇区的照片，加上相邻扇区 10° 以内的照片。
   - 总数 ≥ 24 张、就绪扇区也够时，触发**全景作业**。
     - 默认要 6 个就绪扇区。
     - 照片满 48 张后，没有照片的方向算作拍不到，要求降为 max(⌈0.75A⌉, A−2, 2)，A 是有照片的扇区数。
   - 之后照片继续增长，立面每多 3 张、全景每多 8 张就重建一次。失败的作业也计入，要等再增长够了才会重试。
5. **作业**（`jobs.py`）：单个后台线程按顺序执行（SfM 很吃 CPU）。
   - 作业做完后会重新规划一次，所以作业运行期间新到的照片不会被漏掉。
   - 服务重启时，未完成的作业会重新排队。但进程已经在同一个作业中途退出过 2 次的，直接记为失败，不再重跑。
   - 只有一条替换规则（`jobs.superseded_by`）：旧作业晚完成时，不会盖掉同一目标更新的已发布模型。已发布的模型含有这次没有的照片、而且这些照片上传得更晚时，这次的模型存为未发布，作业以"已完成"结束并写明原因。
   - 风格化作业排在重建作业后面，见下一节。
6. **重建**（`reconstruct.py`）：
   - pycolmap 提取 SIFT 特征。不超过 60 张时做穷举匹配，更多时按 GPS 做空间匹配。
   - **特征缓存**（`landmark_map.py`，`Params.feature_cache`，默认开）：每个地标一个缓存。它按处理图的 sha256 原样存下 COLMAP 写过的特征、匹配和两视图几何。作业开始前把已有的行写进自己的数据库，COLMAP 只算新的。建图读到的数据库和不用缓存时逐字节相同（验证了 46 个作业），核心五栋的作业 CPU 少了 59.7%。
   - 然后做增量建图，而且不止建一次：不超过 30 张时用 3 个种子各建一次；更多时，只有结果可疑（超过 5% 的相机被标记，或平均罗盘误差超过 20°）才再建一次。最后留下未标记相机最多的模型。建图每次仍从零开始。从目标上一个模型续建（`Params.map_continue`）做了，但开发集验证没过，默认关。
   - 少于 12 张、并且每台相机都有 35 mm 等效焦距时，固定使用 EXIF 焦距。原因是一个近似平面的立面只有几张照片，定不准焦距。
7. **地理配准**（`reconstruct.georegister`，纯 numpy）：
   - 用相机的右向量和相机中心的分布估计重力方向。直接平均"上"向量会因为仰拍偏差约 10°。
   - 用鲁棒的 2D 相似变换把相机中心对齐到 GPS，偏航角再按反方差和指南针融合。没有指南针时，用"伪罗盘"：假设每张照片都朝地标中心拍。
   - 最后按 1.6 m 的拍摄高度确定 z。
   - 输出 ENU 坐标（x=东，y=北，z=上，单位米），以及每张照片估计出的位置和朝向。也就是说，照片的方位由 SfM 自动判断，不只依赖手机的 EXIF。
   - GPS 不够用时，`georegistered` 为 false。不够用的情况包括：内点太少、分布太窄、预计尺度误差太大，或者和罗盘偏航相差超过 40°。这时偏航只靠罗盘或伪罗盘，尺度是粗估的，在真实建筑上常偏大 1.5–2.4 倍。按注册率过门时质量门不检查这一项，所以这种模型也可能发布；D31 的按张数过门要求它为 true。
   - **地理锚点**（`anchor.py`）：配准结果另存成一条锚点记录，和 SfM 自己的局部坐标分开：从局部坐标到 ENU 的相似变换，以及偏航、尺度、水平位置、高度、倾斜各自的 1σ 和来源；每台相机也另记局部位姿。σ 按平方和加上一组下限（`dev-core5-v1`，只在开发集上拟合）。锚点只是把已有的配准记下来，不带来新的偏航或尺度来源，所以模型的绝对位置没有变准。风格化的吸附门和 API 的 `geo` 块读它；质量门只记录、不拦。
   - 配准之后，`camera_flags` 逐台检查相机。离自己的 GPS 超过内点阈值（至少 10 m）、并且和自己的罗盘相差超过 45° 的，标为"双胞胎"，常见于长得像的两个立面。有 2 台以上时，重建会切断它们和其余照片的匹配，再建一次图。
8. **发布质量门**（`qa.py`）：只和产品本来就知道的东西比较（照片的 GPS 和罗盘、地标中心和半径），不需要真值。检查项和门槛：

   | 检查 | 门槛 |
   |---|---|
   | 注册相机 | 至少 3 台；注册率立面 ≥ 60%，全景 ≥ 70%。立面注册率不够时，注册 ≥ 6 台并且地理配准拟合上了 GPS（`georegistered` 为 true）也算过（D31，`qa_face_min_registered`）；`checks["registration_path"]` 记下走的是 `fraction` 还是 `count` |
   | 点数 | ≥ 300 |
   | 平均重投影误差 | ≤ 2.5 px |
   | 双胞胎相机 | ≤ 10% |
   | 带可疑标记的相机 | ≤ 20% |
   | 各相机罗盘偏差的中位数 | ≤ 25° |
   | 点云水平中位点离地标中心 | ≤ 半径的一半 |
   | 全景模型的覆盖 | 就绪扇区数和全景作业的要求相同，每个扇区至少 2 台未标记的注册相机 |

   没过门时：
   - PLY 和 `.json` 照样写盘，`.json` 里 `published` 为 false；
   - 作业记为失败，并写明原因；
   - 之前发布过的版本继续显示；没有的话，这个目标暂时没有模型。

   过门模型里被标记的相机，其位姿不公开。
9. **输出**：
   - `models/<地标>/<模型>.ply` 是带颜色的点云。
   - 同名 `.json` 里有注册数、点数、GPS 残差、朝向误差、每个相机的位姿（ENU 和局部坐标）、是否发布（`published`）、质量门结果、各阶段耗时、地理锚点（`anchor`）和带版本的输入（`inputs`：照片数、其中最新的上传时间、照片集的 sha256）。
   - 发布的 COLMAP 模型另把稀疏模型和 `map.json` 存进 `maps/<地标>/models/<模型>/`，每个目标留最新的 2 个。风格化作业读它。

### 风格化模型（结构优先；作业系统、脚本和基准共用一个入口）

风格化的入口有三个，都调用 `crowd3d.structure_pipeline`：
- **作业系统**（`jobs.py`）：地标有分件快照时，每个发布的 COLMAP 模型排一个风格化作业。
  - 重建作业优先；没有重建作业排队时，才开始风格化作业。
  - 作业在子进程里跑（`python -m crowd3d.structure_pipeline run --spec`），2 个线程，`stylize_timeout_s`（1200 s）一到就杀掉。
  - 子进程读模型存下的地图和照片的处理图，只写自己的工作目录和照片缓存，不碰数据库。
  - 风格化模型过了自己的质检，才写出 GLB。服务把它放到 PLY 旁边，记进 `ModelRecord.stylized`。
  - 目标已经显示更新的模型时，作业以说明结束。子进程失败或超时，作业失败，不写 GLB。
- `scripts/stylize_model.py`：处理单个模型。
- `scripts/benchmark.py`：把测试集上每个发布的模型都风格化一次（基准里产品自己的风格化作业是关的）。

**结构流水线做什么**（[docs/STRUCTURE_FIRST.md](docs/STRUCTURE_FIRST.md) §2.9）：读分件快照并核对 sha256 → 用 `stylize.register_scene` 吸附、过配准门 → 配准被接受、并且分件不超过 60 个时才跑判定器（D15）→ D25 只在有两种可商用天空掩码时跑（今天不跑）→ 发布门检查 → 风格化。没有分件快照时，退回外轮廓拉伸。

**只有一种天空掩码（A+R）时**：天空轮廓线这一路既不能核验也不能投票；D15 不采用整栋外框；D25 不跑。D15 只剩一种组合：SfM 点和三维直线一致，并且读到这块积木自己的屋顶。今天每个真实众包模型都过不了配准门，判定器根本不跑，所以产品给出的都是 OSM 分件的素模。

下面第 1–8 步说明整套设计。在结构流水线里，判定（第 3 步）和 D25（第 5 步）只在配准被接受时才跑。

1. **框架**（`structure.py`）。读地标的 OSM 快照，保留落在主轮廓里的 `building:part`。每块变成"底高到檐口的棱柱 + 屋顶原语"。
   - 高度取自 `height`、`building:levels`、`roof:height` 等标签。
   - 标签缺了，就用屋顶形状的约定比例（D17），或者 3 m 的"高度待定"矮台（D13）。
   - 每个参数都记下来源和状态（体块登记表 v2）。Wikidata 的总高永远不用于单个分件。
   - 快照在 `eval/osm/<slug>.parts.osm`，由 `scripts/trim_osm_parts.py` 从整块下载裁出。
2. **照片证据**。三路共用同一套位姿：
   - 天空轮廓线（`skyline.py`，基于 A+R 天空掩码）；
   - SfM 点；
   - 三维直线（`lines3d.py`）。
3. **判定**（`judge.py`，D15）。下面几个条件都满足，才自动采用照片值：
   - 至少两路给出数值，而且所有给出数值的通道两两相差 ≤ max(1 m, 5%)；
   - 方向相同；
   - 没有顶到搜索边界；
   - 共同尺度没确立时，还要通过尺度无关检查；
   - 父件的改动已被接受；
   - 改高度时（往上、往下都算），一致的证据里还要有一路读到这块积木自己的屋顶（D27）：三维直线的屋脊或顶点，或者这块积木的屋面拟合（`roof_fit.py`，和 D25 同一个拟合，而且离轮廓 ≥ 2 m 的格子里要有点，看得到屋顶本身）。只有天空轮廓线加三维直线的檐口、或者天空轮廓线加 SfM 点的最高处（0.98 分位），都不够，开工单。

   细高构件，以及坐标工单还没结的时候，一律不自动采用。条件不满足时保留地图值，并开一张工单。
4. **立面凹凸**（`relief.py`）。用照片的点量出壁柱、檐带、凹进的开间等。
   - 有 G-R1…G-R7 七道守卫，例如 G-R7 要求量到的边离杆子、树干这类独立物体 ≥ 0.3 m；还有"合并开间"检查。
   - 有三维直线核对的元素照常建。
   - 只凭点建的元素（三维直线只在偶然水平的，即 D24 元素），要求模型自己的数据能确立共同尺度；不满足时不建这类元素。
5. **强证据纠正 OSM**（`correct.py`、`correct_measure.py`、`tilt.py`，D25）。纠正三类值：
   - 分件高度和屋顶高，只往上改（D25-H）；
   - 塔的倾斜（D25-T）；
   - "高度待定"矮台和空隙的体块（D25-B）。

   前提是证据级的配准盒子和尺度无关的参照，并且一致的证据里要有一路读到这块积木自己的屋顶（屋面拟合，或三维直线的屋脊、顶点）。盒子太宽时只采用下界。D25 要两种天空掩码，所以产品里不跑。

   每处纠正都带地图原值和全部数字，可以逐条撤销。另外输出一份建议的 OSM 修正报告；OSM 本身不改。
6. **吸附、配准门和观测判定**（`stylize.py`）。门决定照片证据（D15、D24、D25）能不能用；D29 之前它也决定上色。
   - 模型先按窗口搜索吸附到 OSM 轮廓上。偏航窗口按模型报的偏航 σ 定；模型有地理锚点时用锚点的 σ。
   - 然后过配准门。门本身没有参考位姿，量不了真实误差，它检查的是：
     - 吸附后墙点到轮廓的中位距离 ≤ 1.5 m；
     - 逐边核验：有票的边里 ≥ 60% 的中位距离 < 3 m，通过的边方向至少差 30°；
     - 偏航别名：另一个差不多一样贴合的摆放，如果会把墙上的照片或相机挪动 ≥ 1.5 m，就拒绝；
     - 任务 #73 加的三条（流水线模型才查）：窗口被建筑的对称周期截短、或者模型没报偏航 σ 时拒绝；吸附后相机到自己 EXIF GPS 的中位距离超过 max(20 m, 3 × 锚点在相机处的水平 σ) 时拒绝；
     - 另外还检查 GPS 深度、相机位移、倾斜和可见性。

     基准事后拿参考位姿判"对/错"：相机 ≤ 1.5 m、三维墙点 ≤ 1.5 m 算对。
   - 过门以后判定哪些墙算拍到：要有 ≥ 2 台相机看到、墙上有足够的 SfM 点、拟合的墙面贴着这个面，再按照片之间是否一致、去掉天空和植被，得出每面墙的观测掩码。D24 只在拍到的墙上量，结构指标的"拍到面积"只算它们。照片的颜色只用来判断看到的是不是同一面墙，不进模型；每个面都是素模（D29）。
   - 不过门时整栋不用照片证据：判定器从同一批照片得出的结论（D15 采用、照片核验）全部撤回，没有墙算拍到，不建 D24。D25 的纠正则按配准等级保留，所以素模上也可能带着照片纠正。
7. **诚实检查**。三道检查各管一层：
   - `check_honesty` 查流程本身执行的约束：每个面都有来源、外观都是素模、只有墙能标"拍到"、"高度待定"矮台全是素模、每个凹凸元素都有记录；
   - `audit_model` 用点和相机独立复核拍到的墙的点支撑和遮挡，并核对 D24 的凹凸几何、D25 的每个纠正值都和各自的记录一致；
   - `audit_glb` 只看发布出去的 GLB 字节：没有图片、贴图和纹理坐标，每个节点的来源、每个照片值的证据和记录都对得上。

   这些检查用来抓程序 bug：它们核对记录完整、和模型一致，但不用记录里的数字把判定规则重算一遍，所以挡不住自洽地伪造的记录（D26）。

   另外，`structmetrics.py` 统计每个数字来自 OSM、约定、占位值还是照片。
8. **查看**。GLB 每个节点的 extras 都带来源和证据。在 `web/stylized.html` 里点选一块积木，可以看到它的来源卡片，例如"形状：OpenStreetMap 志愿者测绘"或"照片纠正地图（自动）"。
   - 画风文件在 `web/themes/*.json`。
   - 查看器按面的种类画素模：屋顶一种颜色，其余一种，都带淡斜纹；换画风不用重跑风格化。
   - 画风的校验只查斜纹看得见（ΔE00 ≥ 3，按查看器真实的光照算）和格式，见 [docs/ART_DIRECTION.md](docs/ART_DIRECTION.md)。

## D33：用户协议在登记时同意一次、视角取整到 1°（2026-11-05）

**产品负责人的决定**（原话："用户协议在注册时即同意了。视角我之前就说了用一度。"）。这是对 D32 两个问题的答复（见下面"D32"一节的最后）。

**开发这边的理解**（负责人可以改）：

- 原型没有账号：D32 时每次上传带一个随手填的昵称（`user_id`）和协议版本（`terms`），每次打开地标页都要先勾选同意协议才能上传。所以做一个最小的"上传者登记"：填昵称、同意现在版本的用户协议，服务器记下这次登记，发给浏览器一个保密的登记凭证。以后的上传都带这个凭证，不再每次勾选协议。
- 协议出了新版本时，登记过的人同意一次新版本就行，不用重新起昵称。
- 真正的账号（密码、邮箱）不在这次范围里，负责人要时再做。负责人说的是"注册"；因为没有账号，页面上叫"登记"。
- "一度"也包括视角：公开的视角从取整到 5° 改成 1°。

### 1. 用户协议在登记时同意一次

**地标页的上传卡片**：

- 没登记时，卡片只有登记表单：
  - 一句说明："第一次上传前，先登记昵称并同意《用户协议》。只需登记一次，这台设备会记住。"
  - 昵称（最多 64 个字符，会显示在共同完成者里）；
  - "我已阅读并同意《用户协议》"勾选框（链到协议），下面是它的说明（见下面"说明写明"）。
- 勾选框每次打开页面、每次切换表单都不勾。没勾就不发请求，提示"请先阅读并同意《用户协议》"，并把焦点放到勾选框上。没填昵称时提示填写。
- 登记以后，卡片显示"上传者昵称：<昵称>"和"忘记这台设备上的登记"按钮，下面是选照片和上传。D32 上传区里的勾选框没有了。
- 登记存在这台设备的 localStorage（`crowd3d.contributor`：凭证、昵称、同意的协议版本）。浏览器禁用存储时，登记只在这次浏览里有效，登记成功的提示后面会说"这台设备不能保存登记，刷新后需要重新登记"。
  - D32 时页面记住的昵称（`crowd3d.user_id`）会预先填进昵称框，登记以后删掉。
- 存下的协议版本不是现在的版本时，卡片换成"同意新版本"：上面仍是"已登记的昵称：<昵称>"和"忘记这台设备上的登记"按钮（不想同意新版本的人可以在这里忘掉登记），下面是一句说明"《用户协议》已更新……昵称不变"、勾选框和它的说明、"同意新版本"按钮。
- 上传被拒时：
  - `register_required`（服务器不认识这个凭证）：页面忘掉这份登记，回到登记表单，原来的昵称已经填好，提示"服务器上找不到这台设备的登记，请重新登记"；
  - `terms_outdated`：卡片换成"同意新版本"，提示"还没有上传：先同意新版《用户协议》，选好的照片会保留"（不重复卡片上的说明）。同意以后再点一次"上传"，选好的照片不用重选。
- "忘记这台设备上的登记"只删这台设备上的登记，不用确认。撤回凭证留着，照片仍可以在下面撤回。服务器上的登记不删（见下面的问题 2）。D34 第 2 步起页面会按登记向服务器查照片；忘记以后查不了，所以当时没列在页面上的照片就查不回来了（协议第 6 节写了）。
- 共同完成者里的"（你）"按登记的昵称标。
- 勾选框的说明写明（D32 的内容，D33 改了几处）：
  - 照片会公开，去掉 EXIF 等拍摄信息，长边缩到 1600 像素以内；
  - 拍摄位置（取整到 1 米）、朝向和视角（都取整到 1°）也公开，能确定位置和朝向的照片才显示；

**接口**（API 只发代码，页面按代码翻译，D32）：

- `POST /api/contributors`：`{nickname, terms}` → 201 `{nickname, terms, contributor_token}`，带 `Cache-Control: no-store`。
  - 先查协议版本：缺了或空着返回 422 `terms_required`，别的值返回 422 `terms_outdated`。
  - 再查昵称，用 D32 的 `user_id` 规则：去掉首尾空白后 1–64 个字符，不含控制字符，任何文字都行。也不能含落单的 UTF-16 代理项（JSON 的 `\ud800` 这类转义解出来的，不是字符，存不进库）。不合格返回 422（字段 `nickname`）。
  - 不合格时一行都不存。
  - 请求体由服务器自己读：只认 `Content-Type: application/json`、16 KiB 以内、顶层是对象的 JSON，别的都当作空的请求体（返回 `terms_required`）。协议版本被拒时 `input` 为 null，只回显文字的昵称（下面第 4 部分）。客户端没发完请求体就断开时返回 400 `the request body was cut off`（两个接口都是）。
- `POST /api/contributors/accept`：`{contributor_token, terms}` → `{nickname, terms}`，同意现在版本的协议。凭证缺了、不是字符串、格式不对或不认识返回 422 `register_required`；版本不对返回 `terms_required` / `terms_outdated`，这时登记记录不变。请求体的规则和登记一样，别的形状都当作空的请求体（返回 `register_required`）；422 的 `input` 一律为 null，不回显请求体里的任何内容。
- `POST /api/photos` 的表单现在是 `files`、`contributor_token`、`landmark_id`。凭证最先检查：
  - 缺了、空着、格式不对或不认识：422 `register_required`（`input` 为 null，不回显凭证）；
  - 登记时同意的版本不是现在的版本：422 `terms_outdated`（`ctx` 里是现在的版本和协议地址），要先 `accept`；
  - 这两项都在查文件数和地标之前，被拒时什么都不存、不排作业。
- 照片的昵称（`user_id`）和同意（`location_consent`）都取自登记记录。表单里另带的 `user_id`、`terms` 不读。
- 拒绝用 422 加类型码，不用 401 / 403：和 D32 的 `terms_*` 一样，页面走同一条翻译路径。
- `GET /api/contributors` 是 404：上传者的任何信息都不经 GET 给出。

**登记凭证**：

- 256 位随机数（`secrets.token_hex(32)`，64 位小写十六进制），只在登记成功时给这一次。
- 库里只存它的 SHA-256（`contributors.token_hash`，唯一）。不加盐，也不用公开 id 的密钥：凭证本身是 256 位随机数，没什么可猜的；公开 id 的密钥丢了，也不会让所有人的登记失效。
- 只放在 POST 请求体里（登记和同意是 JSON，上传是表单字段），从不放在地址或请求头里。开发这边对 D33 的理解允许请求头或表单字段；选了请求体，是为了不进日志。
- 任何 GET、点云、GLB、`/poses` 和公开的照片里都没有凭证、它的哈希和上传者 id（泄漏扫描查）；DEBUG 级别的日志里也没有凭证和它的哈希（日志测试查）。凭证字段没有格式约束，被拒时服务器自己写 422、`input` 为 null；登记和同意的请求体由服务器自己读，不交给 FastAPI 解析；上传接口的 422 一律不回显输入（`api.validation_error`；都见第 4 部分）。所以不管请求体是什么形状，这三个接口的 422 都不回显凭证。以前有两个例外：aba2940 时 `accept` 收到的凭证不是 JSON 字符串、或者请求体不是 JSON 时，FastAPI 自己的类型错误会把收到的值原样写回 422，99b57e5 改掉了；fc83755 时上传的凭证作为文件部分发来（凭证在文件名或这一部分的 Content-Type 里），或者凭证写在文本的 `files` 字段里，FastAPI 的 422 会把这一部分写回，ffe2a41 改掉了。
- 代价（设计时实测：在洗礼堂数据库的副本上，用设计的表结构直接写 SQLite，登记 1,000 次）：
  - 登记一次 0.40 ms；
  - 按哈希找凭证 8.7 µs（走唯一索引）；
  - 每次登记约 230 B（1,000 次多 229 KB）。

### 4. 最后几个小问题（评审和第 2 轮截图检查之后）

评审和第 2 轮截图检查留下的小问题，99b57e5 改了（上传后撤回时的结果表到 ffe2a41 才改全、桌面上的拍摄位置表到最后一个提交才改全，见本部分最后）：

- **上传结果表留在新的提示下面**：
  - 问题：上传被拒（`register_required` 或 `terms_outdated`）以后、"忘记"登记以后，卡片上还留着上一次成功上传的结果表，就在新的红色提示下面。表里的照片可能已经撤回了，却仍标着"通过 / 确定了位置和朝向后公开……"。原因：`landmark.js` 的 `onUpload` 只在成功时重画结果表。
  - 改法：结果表只放最近一次上传的结果。卡片不再是上传的状态时（忘记登记、服务器不认识这份登记、要同意新版本）清空（`setContributor`）；每次开始上传时也先清空，所以上传因为别的原因失败（例如连不上服务器）时也不会留着上一次的表。撤回列表不受影响。表还在时撤回表里的照片，那一行原来仍标着"……公开（可撤回）"，99b57e5 没改到，ffe2a41 改了（本部分最后）。
- **`accept` 的 422 回显凭证**：
  - 问题：`POST /api/contributors/accept` 收到的凭证不是 JSON 字符串（数组、对象），或者请求体不是 JSON 时，FastAPI 自己的 422（`string_type`、`model_attributes_type`）把收到的值原样写回响应。
  - 改法：登记和同意两个接口不再让 FastAPI 解析请求体，由 `api.contributor_fields` 自己读：只认 `Content-Type: application/json`（可以带 `charset`）、16 KiB 以内、顶层是对象的 JSON。别的（不是 JSON、表单、multipart、JSON 数组 / 字符串 / 数字 / null、太深的嵌套、别的或没有 Content-Type、更大的请求体）一律当作空的请求体，按原来的类型码拒绝：`accept` 是 `register_required`，登记是 `terms_required`。字段不是字符串时也一样：凭证是 `register_required`，协议版本是 `terms_outdated`。
  - 这两个接口的 422 一律 `input` 为 null（协议版本也不回显：同意的请求体里有凭证），只有登记时文字的昵称照旧回显（用户自己写的）。API 文档（OpenAPI）里两个请求体的格式照旧。
  - 核对：在真实服务上（洗礼堂数据副本，真实 HTTP），对两个接口各发 38 种请求体，再加两种分块传输、凭证放在网址里和 4 种别的方法，另加上传接口 4 种，共 94 个响应。没有一个含凭证或它任意连续 16 个字符（十六进制和十进制写法都查了），登记记录没变，服务日志里也没有；格式正确的请求（带 `charset`）照常通过。
- **桌面上的拍摄位置表**：
  - 问题：卡片宽 640 px 以上时还是表格，360 px 的滚动框把一行从中间截断，没有边框和渐隐（aba2940 只改了窄卡片）；滚动条浮在内容上的浏览器（macOS 默认）看不出下面还有几十行。

### 版本号为什么都不变

- **`RECON_OUTPUT_VERSION` 仍是 2**：
  - 规则是任何可能改变重建输出（稀疏模型、PLY、模型 JSON、质量门结论）的改动都要升版本，改 ingest 也算。

**照片接口**（`GET /api/landmarks/{id}/poses/{公开 id}/photo`，`photoposes.public_photo`）：

- 只按 12 位的公开 id 取，不收库内 id。只给此刻 `/poses` 里那一行的照片：通过、没撤回、在快照里、有确定的位姿。返回前再从库里读一次，确认它还公开着。
- 照片由处理图重新编码：只留 JFIF 头，没有 EXIF（GPS、时间、机型、焦距都没有）、注释、ICC、XMP 和 dpi。长边最多 1600 px，渐进式 JPEG，质量 80；洗礼堂 51 张中位 401 KB、最大 560 KB。处理图里还留着上传者写的 JPEG 注释，所以一定要重新编码，不能直接发处理图。
- 缓存：`Cache-Control: no-cache` 加弱 ETag `W/"<公开 id>.1"`。浏览器可以存着，但每次看都要问一次，所以撤回马上生效：带着旧 ETag 来问，撤回后也是 404。没有 `Last-Modified`，因为处理图的文件时间就是上传时间。
- 其余所有请求都得到同一个 404 `{"detail": "no such photo"}`，不带 ETag 和缓存头。包括：撤回的、没通过的、快照之后才上传的、没有位姿的照片，库内 id，别的地标的行，大写或长度不对的 id。

**照片和素模对照**（风格化查看器的"从这张照片的角度看"，`web/compare.js`）：

- 素模按这张照片的位置、朝向、俯仰、横滚和视角画，画面的宽高比和照片一样，照片放在旁边：宽屏并排，窄屏上下。

- ‹ › 和左右方向键按绕地标的顺序换照片，照片和素模一起换；Esc 返回总览，焦点回到卡片的按钮。

- D30 的规则不变：只有测出了位置、高度、俯仰、横滚、视角和宽高比的行才和素模对照，不用假设的值画。EXIF 行（手机 GPS + 罗盘）和缺测量值的行只有"看照片"：单独显示照片，写明来源、2σ 范围和为什么不能对照。

**浅色 / 深色**：

- 每个页面（首页、地标页、用户协议、风格化查看器）都有"外观"：跟随系统 / 浅色 / 深色，默认跟随系统（`prefers-color-scheme`，系统一改马上跟着变）。

**中文 / English**：

## D30：别人照片的拍摄位置（2026-11-03 决定，11-04 验证）

> **D32（2026-11-05）改了这一节的同意规则**：上传必须同意用户协议（D33 起在登记时同意一次），每张通过、确定了位置和朝向的照片都公开（位置和照片本身），以前的照片一次性迁移成同意。下面"同意和撤回"里的勾选框、`share-location-v1` / `v2` 和"以前的照片都算不同意"都已删掉。取整、快照、扣下的规则和视觉定位没有变。见上面"D32"一节。

**产品负责人的决定**（原话："别人照片的位置取整到 1m、朝向取整到 1°，并且不返回用户 ID。只要用户同意分享位置信息，我们必须不能浪费（做出粗糙的推断）"）：

- "不能浪费"，开发这边的理解：
  - 不显示粗糙的推断，例如"朝着地标中心"这种猜出来的朝向；
  - 每张同意的照片都尽量放准：在已发布的模型里就用模型重建出的位姿，不在就用视觉定位放进地标已存的地图；手机 GPS + 罗盘只作标明了的后备；
  - 放不准就不显示。

**同意和撤回**（D30 的做法；D32 把可选的勾选换成了必须同意的用户协议，见上面"D32"一节）：

- D30 时地标页上传区有一个勾选框"公开这些照片的拍摄位置、朝向和视角"，默认不勾，同意记成 `share-location-v2`（v1 的说明少写了一条风险）。D32 删掉了这个勾选框和这两个版本。
- 说明里写的两条风险，D32 的协议和上传说明都保留了：这里上传的人少时，别人能猜出哪几行是你的；任何人都能用手动重建或几张上传让下一次建模很快开始。
- 只有通过校验的照片才记下同意（D32 起记的是协议版本 `terms-v1`）。
- 上传结果给每张公开的照片一个撤回凭证，浏览器把它存在本机。地标页可以撤回一张或全部，撤回马上生效（`POST /api/photos/{id}/share_location`；D32 起同时撤下照片本身）。D30 时凭证只在上传的响应里给一次；D34 第 2 步起，上传用的登记可以向服务器重新要（`POST /api/contributors/photos`），也可以直接凭登记撤回。

- 共同完成者只列昵称，不给每人的照片数，免得和公开的位置对上号。

**别人看到什么**（`GET /api/landmarks/{id}/poses`；地标页的"公开的拍摄位置"表和点云上的标记；风格化查看器在素模上画出来）：

- 每行有这些字段：
  - 公开 id：用部署密钥算的 12 位，不是库内 id；

**扣下不显示的**（宁可没有位姿，也不画粗糙的）：

  - 代价规则没过：定位要用掉运行 CPU 的 26.7%（dev）和 66.5%（test），上限是 25%。圣家堂一栋每次花约 1,300 CPU 秒，一张也没定位上。

  - 基准给运行里的定位位姿打分；
  - 重复几次全新运行的开 / 关对比。原因是一次打开定位的运行里，模型的轮廓转角从 1.6° 变成了 10.2°，不知道是不是偶然。

## D31：照片资格和立面按张数过门（2026-11-03）

**产品负责人的决定**（原话："照片只有建筑占据主体（或 与被拍摄的建筑 50m 以内）才能算合格的。照片方向集中的建筑，能不能只做照片集中的那一面？反正模型主体你都是从 osm 上面拉下来的。"）：

- 照片资格是定了的：建筑是照片的主体，或者相机离被拍的建筑 50 m 以内，照片才合格。
- "只做照片集中的那一面"是负责人问"能不能"，下面是开发这边的做法：系统本来就按面建立面模型，原来的质量门要立面注册率 ≥ 60%，SfM 只连上一部分照片的面就被扔掉（例如林肯纪念堂东面 30 张里注册上 10 张）。模型主体本来就来自 OSM，所以立面也可以按注册上的张数判，没注册上的照片只是没有 SfM 位姿。

**改了什么**（提交 fcb4fbd、0ebbcc1、081e928、09f7621）：

1. **照片资格**（`crowd3d/subject.py`，拒绝码 `not_subject`）。50 m 量的是相机 EXIF GPS 到建筑 OSM 主轮廓的水平距离，在楼里算 0。"主体"用几何估算：从 GPS 位置看地标的 OSM 分件，建筑在水平或竖直方向上占视场的比例，取大的那个，≥ 1/3 算主体。不看像素，不用罗盘（罗盘只管原来的 `facing_away`）。两条满足一条就合格。地标没有绑定 OSM 轮廓时不查，照片带警告 `subject_unchecked`，网页上写"没有检查建筑是不是照片主体"。只对新上传生效，每张照片存下距离和占比，以后改阈值可以重判。
2. **立面按张数过门**（`qa.py`）。立面注册率不到 60% 时，注册 ≥ 6 张（`qa_face_min_registered`）、并且地理配准拟合上了 GPS，注册这一项也算过。点数 ≥ 300 等其余检查一条不变，全景模型不走这条路。模型的质量门结果记下走的是哪条路（`registration_path`：`fraction` 或 `count`）。
3. **基准**：印度门的参考修成第 2 版，13 台和自己的 GPS 隔着拱门、照片又证明不了参考对的参考相机标成未验证（[docs/BENCHMARK.md](docs/BENCHMARK.md) 7.3 节）。通过标准 `eval/criteria/d31-v1.json` 在全新运行之前写好，对比的是 F。

**全新运行的结果**（2026-11-03 到 11-04，提交 09f7621，每栋 2 次，和 F 比；样本内：阈值是看了 F 在这十栋上的运行定的，留出五栋对 D31 只是复现测量）。完整的表在 [docs/BENCHMARK.md](docs/BENCHMARK.md) 6.11 节。

- **结论是 FAIL。** dev（核心五栋）全部通过；留出五栋那一对有三条规则不过；synthetic-v1、mdx-two-v1 是证据不足（和 F 自己比自己一样缺数据）。不过的三条：

## HTTP API

除了照片接口（JPEG），所有接口都是 JSON。时间是 unix 秒，角度是度，距离是米。字段的完整定义见 `crowd3d/api.py`。

API 只发代码和英文的技术说明，没有中文（D32）：拒绝码、警告码、作业状态、作业错误和 422 的 `type` 都由网页按页面语言翻译（`web/api.js`）。用户自己写的内容（地标名、昵称、文件名）原样返回。

所有接口共用的规则（D34）：
- 请求体上限按路由分：只有 `POST /api/photos` 可以到 50 × 25 MB 加 1 MiB，其余请求一律 64 KiB。超出返回 413 `{"detail": "request body over N bytes"}`：带 `Content-Length` 的不读请求体就拒绝，不带的读到超过上限为止，都不解析。不带 `Content-Length` 的请求体如果在服务器已经开始回答之后才超过上限，就不是 413 了（实际只有带着分块请求体去取文件的 GET：发文件时服务器会读请求体）。这时回答照常发完，超出的请求体读了就丢，不交给应用；这样的请求得到 413 还是整个文件，看请求体和回答谁先到（D34 整体验证之后）。发压缩形式的文件时（见下面"压缩"一条）先读完请求体再回答，所以超限一定是 413。
- 上传接口的表单另有自己的上限（D34）：文本字段最多 8 个、每个最多 4 KiB，文件部分最多 50 个；一个文件部分超过 64 KiB 就写到临时文件，不放在内存里。解析到第一个超限的地方就停，后面的请求体不读。文本字段超限返回 413 `{"detail": "upload form over 8 text fields, or a text field over 4096 bytes"}`；文件超过 50 个时的回答和顺序同以前（先看凭证，再说文件个数），只是凭证要排在第 51 个文件之前才读得到：客户端要把 `contributor_token` 放在文件前面（网页是这么发的），不然登记过的人传 51 个文件得到的是 `register_required`。不是 multipart 的请求体不读，照旧是 422（缺 `files`）。
- 422 的每条错误最多回显 1 KiB 的 `input`（按响应里的 JSON 字节算），超过就是 null。请求体里可能有登记凭证的接口一律不回显：上传、撤回、登记名下的照片、同意新版本的 422 `input` 都是 null（登记接口只回显文字的昵称）。404 里引用的地标 id、作业 id 最多 80 个字符。
- 每个响应都带 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin` 和 `Content-Security-Policy`。页面的策略只允许本站的脚本、样式和请求，内联块按哈希放行，图片另允许 `data:`、`blob:` 和地图瓦片；其余响应（JSON、照片、模型文件、错误）一律 `default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`。
- FastAPI 自带的 `/docs` 和 `/redoc` 不提供（它们从 CDN 加载脚本）；`/openapi.json` 照旧。
- 网页文件（`web/` 下的每个文件，含 `web/vendor/` 里的库）带 `Cache-Control: no-cache`：浏览器每次用之前凭 ETag 问一次，没变返回 304。模型文件和照片接口的缓存规则各管各的。
- 压缩（D34 第 4 步）：网页的文本文件（`.html`、`.js`、`.mjs`、`.css`、`.json`、`.svg`，含 `web/vendor/` 里的库）和 `/files/models` 下的 `.glb`、`.ply`，在请求的 `Accept-Encoding` 允许 gzip、文件在 1 KiB 到 8 MiB 之间、请求不带 `Range` 时压缩着发（`Content-Encoding: gzip`，带准确的 `Content-Length`）。一个文件的两种形式各有 ETag（压缩的那个在引号里多 `-gzip`），都带 `Vary: Accept-Encoding`；`If-None-Match` 和这个请求会得到的那种形式的 ETag 比。带 `Range` 的请求得到没压缩的字节。API 的 JSON、错误响应、照片接口和别的文件类型（PNG 等）不压缩。只有 gzip，没有 brotli。

公开的拍摄位置（`GET /api/landmarks/{id}/poses`，D30）只有一种受众，没有参数：
- 只列通过校验、没撤回的照片（`records.location_shared`：照片的同意是 `records.TERMS_VERSIONS` 里的协议版本）。D32 起上传必须同意用户协议（D33 起在登记时同意一次），所以每张通过的照片都算同意，其中确定了位置和朝向的才成为一行（见下一条）；D32 之前的照片在第一次打开数据库时迁移成同意。
- 每行只有 `id, src, p, yaw, pitch, roll, hfov, aspect, sp, sy`：`id` 是用部署密钥算的 12 位 HMAC（不是库内 id），`src` 是 `sfm`（模型重建）、`loc`（与模型比对：视觉定位作业把照片定位到地标的已存地图里，`Settings.localize_photos` 默认关，关着时没有，以前存下的定位结果也不显示）或 `exif`（只用指南针标为真北的手机 GPS + 罗盘，没有高度）；位置取整到 1 米，朝向、俯仰、横滚取整到 1°，水平视角取整到 1°（D33；之前 5°），`sp`/`sy` 是 2σ 范围，按取整放宽后向上取整。按 `id` 排序，不带上传者、时间、模型或扇区。拿不准的（只有 GPS、磁北或没标的指南针、框架没定住的模型、被标记的相机）不列，只计入 `counts.not_determined`。
- 坐标是地标 ENU（米），也就是风格化 GLB 的坐标系：风格化作业接受了外轮廓吸附的模型，相机（以及定位到它里面的照片）跟着吸附移动。
- `loc` 行来自视觉定位作业存下的结果（定位作业是内部的：不在上传结果、详情里，`/api/jobs/{id}` 对它返回 404）；结果一存下就算，但照片和其他行一样要在快照里。
- 这是一张快照：只含最近一次重建作业（立面或全景，成功或失败）结束前上传的照片（`as_of` 是那个时刻），所以单独一次上传不会让列表变化；撤回同意则马上生效。但任何人都能让下一次作业很快结束（手动重建，或者自己上传几张照片），所以一个新昵称刚出现时，紧接着出现的行仍可能和它对上；用户协议第 7 节和上传说明写明了这一点（`terms-v1`）。照片接口用的是同一张快照：一行在 `/poses` 里，它的照片才能取到。
- `uncertainty.measured_coverage` 是各来源在基准测试地标上实测落在范围内的比例（commons-ten-v1 测试集，D31 全新运行按 D30 规则重算，两次运行合计：模型重建 146/165，单栋单次最低 1/10、最高 13/13；手机 GPS + 罗盘 23/28，最低 1/2、最高 1/1；与模型比对在测试集上还没有有参考的定位位姿，没实测，而且视觉定位关着）。D30 的验证在 716de16 上重算了一遍，逐张相同。`rule_calibrated_here` 说这个来源的误差规则是不是用这些地标的照片标定的：EXIF 是（样本内，地标页写明"不是独立检验"），模型重建不是。`counts` 给出快照里通过的照片数、公开的（D32 起就是没撤回的）、显示的、各来源的和没显示的。

ModelInfo（Summary 的最新全景模型、Detail 的模型列表）有两块和风格化、地理位置有关：
- `stylized`：
  - `status` 为 `ready` 时，`url` 指向 `/files/models/…/<模型>.glb`，`registration` 是 `{accepted, reason}`（`reason` 也照上面换掉路径和库内 id；网页按 `accepted` 写"素模（照片已对齐）"或"素模（照片未对齐）"，D32 起 API 不再发中文的 `label`），`poses_url` 是地标的公开拍摄位置（风格化查看器的链接带上 `&poses=`），`snapped` 说这个 GLB 的外轮廓吸附有没有被接受（接受了，这个模型的相机在公开拍摄位置里跟着吸附移动，点云却没动，所以地标页不在它的点云上画拍摄位置，改为提示去风格化模型里看）；生成中时 `snapped` 为 `null`；
  - `status` 为 `pending` 时，风格化作业正在排队或运行；
  - 没有、也不会有风格化模型时为 null。
- `geo`：按现在的下限算出的地理锚点。
  - 字段：`level`（full / prior_only / none）、各分量的 1σ `sigma`、来源 `source`、`calibration_id`、点中位处的水平和竖直 σ `position_sigma_m`、`calibrated`；
  - `calibrated` 只在标定 id 列在 `Settings.calibrated_anchor_ids` 里时为 true。这个列表现在是空的，所以地标页不显示"位置 ±X 米（1σ）"；
  - 锚点出现之前的模型为 null。只供显示，质量门不读它。

结构框架本身没有 API，也没有"重新风格化"的接口。

## 配置

产品阈值在 `crowd3d/config.py` 的 `Settings` 里。命令行只开放了数据目录和重建器两项，其余字段在代码里构造 `Settings(...)` 时修改。环境变量 `CROWD3D_STRUCTURE_CATALOG` 可以换一个地标目录，设成空值就关掉风格化作业；`CROWD3D_KEEP_WORK_DIRS=1`（或 `true`、`yes`、`on`）保留每个作业的工作目录（D34）。

其他参数：
- `crowd3d/params.py` 的 `Params`：算法内部参数，例如 GPS 和罗盘的 σ、RANSAC 门槛。和这一轮有关的几项：
  - `feature_cache`（默认 True）：地标特征缓存；
  - `map_continue`（默认 False）：从目标上一个模型续建，开发集验证没过；`map_rebuild_ratio`（1.5）、`map_max_continuations`（4）等是它的规则；
  - 地理锚点的下限：`anchor_yaw_floor_deg` 7.35°、`anchor_scale_floor` 0.352（log 尺度）、`anchor_xy_floor_m` 3.1 m、`anchor_tilt_floor_deg` 1.94°，高度 σ `anchor_z_sigma_m` 1.5 m，这组下限叫 `anchor_calibration_id` = `dev-core5-v1`。
- 基准的 `eval/configs/*.json` 只写要改的字段，没写的保持默认值。可以改的有：重建器、`Params`，以及 `Settings` 的产品阈值。不能改的是数据放在哪、进程怎么跑、产品自己的风格化步骤和只供显示的字段：`data_dir`、`reconstructor`、`inline_jobs`、`keep_work_dirs`、`max_job_attempts`、`max_concurrent_decodes`、`malloc_mmap_threshold_bytes`、`stylize_published`、`structure_catalog`、`structure_bindings`、`stylize_timeout_s`、`calibrated_anchor_ids`。
- 风格化和结构优先各模块的参数，都在代码里：
  - `crowd3d/stylize.py` 的 `StyleParams`（默认 `DEFAULT_PARAMS`），包括 #73 的三个开关 `snap_use_anchor`、`snap_refuse_clipped_window`、`snap_max_gps_median_m`（20 m），默认都开；
  - `crowd3d/structure_pipeline.py` 的 `Limits`（每个模型 1200 s、4096 MB、最多判 60 个分件，D25 `auto`，掩码只有 A+R）；
  - `crowd3d/structure.py` 的 `StructureParams`（`DEFAULT_STRUCTURE`）；
  - `crowd3d/relief.py` 的 `ReliefParams`（`DEFAULT_RELIEF`）；
  - `crowd3d/lines3d.py` 的 `LinesParams`（`DEFAULT_LINES`）。

## 原型的局限

- **真实照片只测了十栋建筑，阈值是样本内的。** 发布质量门、风格化配准门、#73 的开关和锚点下限都是在开发集（核心五栋、合成集、mdx-two-v1）上定的；D31 的占比 1/3、按张数的 6 张和印度门参考的修正，还看了留出五栋上 F 的运行。留出五栋先只用冻结的提交跑过 B0 和 F，F 有三栋（林肯纪念堂、印度门、悉尼歌剧院）一个模型都不发布，所以那时留出集上的通过标准和标定都是"证据不足"（[docs/REVIEW_ADOPTION.md](docs/REVIEW_ADOPTION.md)）。D31 的全新运行在这五栋上只是复现测量：林肯纪念堂、印度门有了模型，悉尼歌剧院仍然没有。
- **按张数发布的立面，墙可能偏离轮廓（D31）。** 质量门没有一项拿墙和 OSM 轮廓比。D31 全新运行里，圣家堂新显示的南面、西南面两个按张数过门的立面，位姿对，墙却大段不在轮廓 1.5 m 内（地理坐标里超出 5 m），test 上的两条覆盖守卫因此不过；林肯纪念堂的两个张数模型，自己的相机只对 19 / 39。
- **公开的拍摄位置，范围诚实但宽（D30）。** 显示的位姿约三分之一离参考超过 10 米或 15°，86–88% 落在自己标出的 2σ 范围里。手机 GPS + 罗盘那一行在留出集上 14 张有参考的只有 1 张在 10 米 / 15° 内。同意公开的照片里，dev 每次运行约 3/10、test 约一半只有 GPS、没有可用的罗盘，不显示。视觉定位能多放准的很少（约 1%），代价又超标，默认关。
- **模型没有颜色（D29，2026-11-03）。** 产品负责人决定放弃给模型上照片颜色，上色代码已删：GLB 里没有贴图，每个面都是素模，地标页的标签都是"素模（…）"。靠颜色才认得出的地标（洗礼堂的黑白条纹）只剩形状。照片拍到哪些墙只用于 D24 和结构指标，屋顶从不算拍到。
- **真实众包模型用不上照片证据。** 配准门要求相机位置误差 ≤ 1.5 m；拍摄者离墙 40–90 m 时，只靠 OSM 轮廓和手机 GPS 证明不了这么准，所以真实建筑的模型一个都过不了门，D15、D24 用不上这些照片（D29 前：一面墙都不上色）。八边形这类轮廓（洗礼堂）在锚点的偏航 σ 下，窗口会被对称周期截短，众包模型的吸附都会被拒。要让照片证据进来，需要不靠轮廓的偏航和尺度来源（[docs/VISUAL_LOCALIZATION.md](docs/VISUAL_LOCALIZATION.md) 的视觉定位；D30 只实现了给照片定位、只用于显示的那一小块，不给模型提供偏航和尺度），或者产品决定放宽标准。
- **模型在地图上的位置不确定度现在报出来了，而且很宽。** API 的 `geo` 块给出每个分量的 σ。尺度 σ 的中位数约 ±43%；在核心五栋上，点中位处的水平 σ 中位数是 16.9 m（7.7–47.1 m），大部分来自尺度。F 在留出集上标定证据不足，匈牙利国会大厦的水平 σ 还说小了（6 个模型里 4 个在 3σ 外）。D31 的全新运行在留出集上有 22 个可核对的模型：四个分量的 2σ 覆盖都过，3σ 外的比例只有水平位置不过（1.5 / 22，全是匈牙利国会大厦西面）。所以地标页的"位置 ±X 米（1σ）"仍然关着。锚点也没让位置变准：地理相机误差的中位数 dev 6.58 m、test 15.07 m，评审之前是 5.99 m、15.78 m。
- **配准门的已知漏洞（任务 #73）已经修了，但"0 个错误通过"仍只对已记录的运行和对抗用例成立。**
  - 现在门读锚点的偏航 σ；窗口被对称周期截短、或者模型没报偏航 σ 时拒绝；吸附后相机离自己 EXIF GPS 的中位距离太远（> max(20 m, 3 × 锚点的水平 σ)）时拒绝。对抗用例里错误通过从 69 个降到 0 个。代价是精确别名那组里本来对的 78 个通过只剩 16 个。
  - `scripts/stylize_model.py --snap-from` 复用旧吸附前，流水线模型要先按现在的门重新核对。
  - 几处吸附门检查（决定能不能用照片证据）还没有回归测试。真实模型没有一个走到门的"通过"分支，所以开关的好处在真实数据上看不出来。

  D25 也依赖这一点：近圆形的轮廓（洗礼堂有 23 个对称别名）上，纠正要在所有别名转角下都成立才采用。
- **框架几乎全部来自 OSM，照片的贡献很小。** 结构优先让模型认得出来了，例如亚琛的分件、穹顶和尖顶，但形状主要是 OSM 志愿者画的。照片的贡献：
  - 洗礼堂：打开 D24 以后，85 个数字里有 36 个来自照片，大多是立面凹凸。
  - 亚琛：D24 的尺度条件不满足，没有打开；D25 只纠正了一处，唱诗堂顶高"至少 36.26 m"（OSM 写 32 m），照片数字从 0% 升到 0.21%。
  - 比萨：D25-T 只在参考模型上通过，量出倾斜 4.59°，朝 177.0°（公开值约 3.97°）。已发布的众包模型都不带倾斜：它们只拍到塔的一面，点云轴不够准。
  - 洗礼堂上 D25 没有改任何值。
  - 以上数字都来自参考场景（全部照片、已知位姿），而且另用了研究用的第二种天空掩码 Dm+R。只用产品的 A+R 时，洗礼堂和亚琛的参考场景上照片数字都是 0，D25 不跑。众包等级上的 D25-H 和 D25-B 本来也关着。

  OSM 没画分件的建筑，只能把外轮廓拉伸成体块；标签缺了的地方，用约定比例或 3 m 的"高度待定"矮台代替。只在 Wikidata 有条目、地图上没有轮廓的地标还不支持。
- **结构优先接进了产品，但只给出 OSM 分件的素模。**
  - 产品给的：有分件快照的地标（目录里 13 个），每个发布的 COLMAP 模型一个 GLB，带 OSM 分件的体块、屋顶原语和来源，标"素模（照片未对齐）"。风格化作业的子进程 CPU 中位数 4.9 s、最多 19.7 s，峰值内存不超过 300 MB（核心五栋的 20 个模型）。
  - 产品不给的：照片量出的数字（照片颜色 D29 起本来就不给）。原因有两个：每个真实众包模型都过不了配准门，判定器不跑；只有一种可商用的天空掩码，按"两种掩码"的规则，D25 不跑，天空轮廓线一路不起作用。
  - 没有分件快照的地标不出 GLB。
  - 没有"重新风格化"的入口：这个功能上线以前发布的模型，以及分件快照或风格化代码改了以后的模型，要等下一次发布才有新的 GLB。
- **D24 和 D25 按放宽后的标准运行（D26，2026-10-28）。** 对抗加固做了五轮也没有收敛，产品负责人决定放宽标准：
  - 只为合成攻击场景或伪造记录加的守卫都删掉了，D25 也不再往下改高度。真实数据的结果和清理前逐项相同，发布出去的 GLB 二进制部分逐字节相同。
  - 已知能骗过 D25 的合成情形：树冠盖满平顶、脚手架网围住"高度待定"矮台、网加临时顶棚的整体围护。它们会发布比真值高的值或下界。完整列表见 [docs/STRUCTURE_FIRST.md](docs/STRUCTURE_FIRST.md) §2.4.8 第十五部分。
  - 发布检查不防伪造记录。
  - D15 改高度现在要读到这块积木自己的屋顶（D27，2026-10-28）。合成场景里，离墙很近的脚手架网顶、女儿墙不再被当成檐口采用；代价是屋顶从地面看不见的平顶分件，以及小于约 8 m × 8 m 的分件（除非三维直线量到屋脊或顶点），D15 不再改。树冠盖在屋顶上时，树冠上的点能拟合出一个"屋面"，D15 仍可能采用树冠的高度。
- **全景模型在真实建筑上一次都没发布过**，每栋却要花 15–24 分钟反复尝试。不设上限跑完的勃兰登堡门和圣母教堂也没发布。游客只拍"好看的那一面"，很多方向几乎没有照片。
- **采集端**：
  - 只收相机原图：没有 EXIF 判 `no_exif`，EXIF 里没有 GPS 判 `no_gps`。截图、修图软件或聊天软件转存的副本，通常两样都没有。
  - 手机浏览器从相册选图时，可能会去掉 GPS，Android 上很常见。Commons 上也只有约 1/7 的照片带 GPS。
  - 不支持 HEIC，因为没有安装 HEIF 插件。
  - 磁北朝向只给出警告，没有做磁偏角修正。
- **几何**：
  - 重力方向的估计假设手机竖直拿、地面大致水平，单个立面可能残留几度的倾斜。勃兰登堡门的模型相对参考的中位倾斜是 3.4°，原因没查清。
  - 无法地理配准时，回退方案的尺度比较粗略。
  - 重建只输出稀疏点云，没有稠密重建和 3DGS。[docs/PHOTOREAL_LOCAL.md](docs/PHOTOREAL_LOCAL.md) 说明怎样导出数据，在本地用 GPU 训练 3DGS。
- **重建**：只用 CPU，单线程串行。特征和匹配现在有地标级缓存，但建图每次仍从零开始，没有增量注册：续建做了，可是开发集验证没过（版本连续性 56%，要求 90%；先试续建再从零重建，净省的 CPU 为零），默认关。用缓存时，不设上限跑完勃兰登堡门（150 张照片）要 1,345 s 墙钟，圣母教堂（111 张）要 3,953 s。
- **服务**：单机 SQLite 加本地文件，一个数据目录只能由一个服务进程使用。没有账号和内容审核。上传要先登记（D33）：只有昵称加同意用户协议，没有密码和邮箱，昵称可以重名；登记的凭证存在浏览器的 localStorage 里，库里只存它的哈希；还没有办法吊销被盗的凭证，也不能在服务器上删除登记或改昵称（D33 一节）。别的写操作（建地标、手动重建）仍不用认证。登记和上传都没有限流。登记的凭证只放在 POST 请求体里，不进地址、请求头和日志，422 也不回显它（D33 一节）。撤回靠这台设备：登记还在，就能向服务器查回用它上传的照片并撤回（D34 第 2 步）；清空了浏览器存储或换了设备，登记本身就没了，只能联系运营方，而运维还没有下架命令；这个查询接口不分页。上传的单次请求最多 50 × 25 MB，别的请求最多 64 KiB，超出时在写盘和解析前返回 413（D34；回答开始之后才超限的请求体不是 413，读了就丢，见 HTTP API 一节）。上传表单的文本字段最多 8 个、每个 4 KiB（D34）。同时让 Pillow 处理的上传最多 2 个（`max_concurrent_decodes`，读文件头和解码都算）；贴着像素上限的 WebP 一次解码仍要约 0.9 GB 内存，所以解码最多占约 1.6 GB（实测；靠服务启动时管住 glibc 的分配器，别的 C 库上没有这个保证）。排队的上传各自拿着自己的文件，最多 40 个 × 25 MiB，约 1 GB；限制同时处理的上传个数是上线前事项。EXIF 由自己的读取器读，工作量有上限；文件头超过上限的图在 Pillow 打开之前就拒绝，上限以内最贵的文件头（一个 24 MB 的 PNG 文本块）实测 0.16 秒、多占 114 MB（D34）。模型点云、风格化 GLB、每张通过、没撤回、确定了位置和朝向的照片（去掉元数据、缩小）和它取整后的位姿（D30、D32、D33）对所有人公开；撤回的和没通过的照片什么都不公开。公开位姿的快照可以被任何人用手动重建或几张上传提前更新，上传的人少时公开的行可能和新出现的昵称对上（D30 一节）。照片接口每次请求都重新编码（中位约 105 ms），没有限流；运维还没有下架某张照片的命令，只有上传者能凭撤回凭证撤回。用户协议是草案，等法律审核；D32 的一次性迁移上线前要删掉（D32 一节）。进程崩溃中断的作业最多重跑 1 次，同一个作业被中断 2 次（`max_job_attempts`）后判为失败。`work/` 目录在作业结束后自动清理（`keep_work_dirs` 或环境变量 `CROWD3D_KEEP_WORK_DIRS=1` 可保留）；风格化作业失败时，原因先存到模型旁边再清理（D34，见"数据目录"）。`maps/` 下的特征缓存不淘汰，每张照片约 1.1–1.7 MB。
- **基准**：`scripts/benchmark.py` 的默认数据目录写死成开发机上的一个临时目录，在别的机器上要设 `CROWD3D_TESTSET_ROOT`、`CROWD3D_BENCH_DIR` 或每次传参数；新重建器要改代码注册；风格化的参数还不能通过配置调；逐照片指标还不按"没见过的摄影师"分开报。
- **网页**：地图底图依赖 OSM 公共瓦片（Leaflet 和 three.js 由服务自己提供，不再依赖 CDN，D34）；网页文件和模型文件用 gzip 压缩着发（D34 第 4 步；`three.module.js` 每个新访客传 0.26 MB），没有 brotli，API 的 JSON 不压缩，页面的 `import` 仍是一个接一个发的；内容安全策略只在 Chromium 里实测过，而且拦不住页面跳转（见 [docs/decisions/D34-review-fixes.md](docs/decisions/D34-review-fixes.md) 第 3 步）。地标页点云上画的是全部公开的拍摄位置，不按立面分开；风格化模型吸附过的，点云上不画（点云没有跟着吸附移动），改为提示去风格化模型里看。
  - 只有中文和英文（D32）。
  - "公开的拍摄位置"表在卡片窄于 640 px 时（手机，或 700–1024 px 宽时的主栏）每行竖排、值前写列名，不用横着滚动；360 px 的滚动框有边框，底边的渐隐标出被截断的一行（D33；D32 时手机上要横着滚动才看得到朝向和 ±范围）。不支持 CSS 容器查询的旧浏览器还是表格，要横着滚动。卡片宽 640 px 以上时还是表格，滚动框也有边框和底边的渐隐，框高 376 px，被截断的那一行透过渐隐看得见（D33）。
  - 风格化查看器的语言和外观切换在面板里：模型加载中、加载失败和 `ui=0` 时没有切换（选择和别的页面共用）。

## 下一步

外部评审采纳计划的结论和下一步见 [docs/REVIEW_ADOPTION.md](docs/REVIEW_ADOPTION.md) 第 5、6 节。

D31 的全新运行按 `d31-v1` 是 FAIL（见上面"D31"一节）：照片资格的两个默认取法，以及按张数过门新显示的立面墙放偏了以后还要不要保留这条路，都等产品负责人决定。

D30 的两个问题（只有手机 GPS + 罗盘的位姿要不要显示、共同完成者的昵称要不要留）现在用默认答复，等负责人决定；视觉定位按 `d30-v1` 保持关闭（见上面"D30"一节）。

D32 的两个问题 D33 已答复：视角取整到 1°，用户协议在登记时同意一次，都已实现；上线前要删掉一次性迁移、请律师审核用户协议、加照片下架的命令和照片接口的限流（见上面"D32"一节）。

D33 的两个问题（昵称要不要唯一、能不能在服务器上删除登记或改昵称）现在用默认答复（都不），等负责人决定；上线前还要给登记加限流、加吊销被盗凭证的办法（见上面"D33"一节）。

1. **视觉定位**（[docs/VISUAL_LOCALIZATION.md](docs/VISUAL_LOCALIZATION.md)；D30 只做了给同意公开的照片定位、只用于显示的那一块，默认关，§10）：新照片对已配准的地标级模型做绝对定位，让没有 GPS 的照片加入模型，同时提供不依赖轮廓的偏航和尺度。D30 测出的第一个障碍是代价：每张查询要和地图里每张照片匹配，大多数最后配不上，先要做检索。这是唯一能改变绝对位置和配准门结果的路，也是照片证据（D15、D24、D25）进入真实众包模型的前提。底子已经有了：每个已发布模型的稀疏地图存在 `data/maps/<地标>/models/` 下，锚点是独立的记录。
2. **单掩码的决定（D28）**：要么保留"两种掩码"的规则（现在的默认），要么让 A+R 单独算一路、门槛更严，后者要有自己的一轮验证。先要一个研究开关，把 A+R 自己的读数报出来才能权衡。另一条路是查清 Dm+R 或 C+R 的许可，得到第二种可商用的掩码。
3. **续建要一个更好的接受规则**：例如只在照片数超过 30 张时续建（小照片集保留三个种子的多样性），接受续建的门槛不用 `suspicious()` 的 5%，再定完整模型的重试规则（[docs/BENCHMARK.md](docs/BENCHMARK.md) 6.8 节末尾）。改完要重新过开发集验证。
4. **评审里需要 GPU 的阶段**：GPU 特征和匹配（如 ALIKED + LightGlue）、稠密重建或 3D Gaussian Splatting。这台机器只有 4 核 CPU，验证不了；到有 GPU 的机器上时，同一个划分和 `review-v1` 可以直接拿来比。
5. **留出证据太少**：F 在五栋里有三栋一个模型都不发布；D31 之后只有悉尼歌剧院没有模型，但可核对的模型够 3 个的也只有圣家堂、印度门两栋，仍凑不出标定要求的"至少 3 栋、每栋至少 3 个模型"，而且这五栋对 D31 已经"烧掉"了。要加建筑，发一个新的测试集或划分版本，并用真实建筑做一次小规模实地采集，重新校准阈值，包括 GPS σ、模糊度和重复判定。
6. **引导拍摄**（方向 B）：采集端改为页面内拍摄，同时记录 GPS 精度、指南针和重力方向（DeviceOrientation），提示"还缺哪几面、哪几块积木还没被拍到"。
   - 这样可以绕开相册丢失 GPS 的问题，提高重力和朝向的先验。
   - 照片能给框架提供的证据也会更多。
7. **产品的缺口**：加"重新风格化"的入口；在现有的发布质量门之上，加"新版本模型不比旧版本差"的比较；完整模型一次都没发布过却占大量作业时间，要改它的重试规则。
8. **照片位姿的公开接口**（任务 #87，D30，见上面"D30"一节）：已经做完并验证。登记时同意用户协议（D33；D32 时是每次上传都同意）、撤回，`/poses` 接口和照片接口（D32），地标页的表和点云标记，素模上的图层和照片对照（D32），指标第 8 版按别人看到的那一行打分。还没做的：视觉定位默认关（要一个便宜得多的定位器、`run` 给运行里的定位位姿打分、重复的全新开 / 关对比，再按 `d30-v1` 重判）；定位表里旧地图键下的记录没人删（照片后来有了 SfM 位姿时不显示，但留在库里）；没有焦距或地图的照片每次候选地图变了都要建一个定位作业记一遍跳过；负责人的两个问题还用默认答复。
9. **平台**：改用 Postgres + 对象存储，加作业队列和多个 worker，加账号、限流、人脸和车牌打码、隐私收紧，以及反作弊。

各阶段的路线图见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) 第 10 节。
