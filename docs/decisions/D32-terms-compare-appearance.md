# D32：上传必须同意用户协议、照片和素模对照、浅色 / 深色和中英文切换（2026-11-05）

> 原来是 README 的一节，D34 C 部分第 2 步（2026-11-13）搬到这里：文字没有改，只把指向 README 别的章节的话（"见上面某一节"）换成了链接。全部决定的索引在 [README.md](README.md)。

**产品负责人的决定**（原话："修改D30:上传的照片必须同意「公开拍摄位置」。这写在用户协定里。「从这张照片的角度看」的UI将照片和模型视角放在一起对比。网站方面，增加常规和夜间模式的切换（默认跟随系统）。同时把网站的语言独立出来也是可以切换的（默认跟随系统）。目前支持英文和中文。"；补充："不用考虑以前上传的照片 - 网站还没上线，现在所有的都是测试照片，可以直接把他们改成同意公开位置"）：

- 上传必须同意用户协议，协议写明拍摄位置会公开。上传时不能选"不公开"。
- "从这张照片的角度看"把照片和从同一位置看到的素模放在一起对比，所以照片本身也公开（去掉 EXIF、缩小），协议写明这一点。
- 每个页面加浅色 / 深色切换和中文 / English 切换，默认都跟随系统。
- 以前上传的都是测试照片，没有历史包袱：全部算作同意。
- 开发这边保留的默认做法：上传以后仍可以撤回，撤回同时停止公开这张照片的位置和照片本身（和 D30 一样马上生效）。

**对上传者变了什么**（地标页）：

> **D33 已取代每次上传时的勾选**：用户协议改在登记时同意一次，上传不再带 `terms`，服务器查登记记录里同意的版本（见 [D33 的记录](D33-registration-fov.md)）。下面前三条是 D32 时的做法；勾选框和它的说明移到了登记表单里。

- 上传区的勾选框换成"我已阅读并同意《用户协议》"，链到协议页。没勾就不发请求，页面提示"请先阅读并同意《用户协议》"并把焦点放到勾选框上。（D33：这个勾选框在登记表单里，只在登记时勾一次。）
- 服务器也检查，不只靠页面：表单字段 `terms` 必须是现在的协议版本 `terms-v1`。缺了或空着返回 422 `terms_required`，别的值返回 422 `terms_outdated`，这时什么都不存、不排作业。（D33：登记时查 `terms`；上传查登记的凭证和它同意的版本，返回 `register_required` 或 `terms_outdated`。）
- 勾选框每次打开页面都不勾；同一次浏览里勾过以后，继续上传不用再勾。浏览器不记"同意过"（负责人问题 2）。（D33：这台设备记住登记，不再每次上传都同意。）
- 勾选框下面的说明写明（D33 起是登记表单里的说明）：
  - 照片会公开，去掉 EXIF 等拍摄信息，长边缩到 1600 像素以内；
  - 拍摄位置（取整到 1 米）、朝向（1°）和视角（1°，D33 起；D32 时是 5°）也公开；
  - 只显示能确定位置和朝向的照片（D33 加上）；
  - 昵称出现在共同完成者里，但不显示哪张照片是谁传的、什么时候传的；
  - 要等这里下一次建模结束后才显示，但任何人都能用手动重建或几张上传让下一次建模很快开始，所以别人可能把那时新出现的照片和你的昵称对上，这里上传的人少时更容易；
  - 不同意就不能上传（D33：不能登记，也就不能上传），上传后可以在这台设备上撤回。
- 通过的照片都算同意公开，等某次建模确定了它的位置和朝向就公开，确定不了的不显示（`/poses` 只列确定了的行，照片接口只给这些行的照片）。D32 时协议第 2 节和这里写的是"每张通过的照片都公开"，和代码不符，D33 改正。上传结果标"确定了位置和朝向后公开，最早在下次建模结束后（可撤回）"（D32 时是"下次建模后公开"），并给出公开 id 和撤回凭证；凭证只给这一次，浏览器存在本机。没通过的照片什么都不公开，也没有凭证。
- 撤回还是 `POST /api/photos/{id}/share_location`，现在一次撤下这张照片的公开位置和照片本身。撤回只是停止公开：照片仍用于建模，昵称也留在共同完成者里，协议写明了这两点。

**用户协议**（`web/terms.html`，中文、英文各一版，版本 `terms-v1`）：

- 11 节：适用范围、照片会公开、拍摄位置会公开、昵称（D33 起是"登记和昵称"）、不会公开的内容、撤回、仍然存在的风险、照片授权、未成年人、协议变更、联系方式。
- 不会公开的内容：哪张照片是谁上传的、上传时间和拍摄时间、照片在服务器内部的编号、原始文件和其中的 EXIF、每人上传的张数、没通过检查的照片。
- 仍然存在的风险：
  - 公开的照片加上公开的模型，任何人都能算出比取整后的数字更准的拍摄位置，取整只限制数字本身透露的信息；
  - 照片内容本身也可能透露信息（人脸、车牌、住处、季节）；
  - 上面说的快照能被别人提前更新。
- **这是草案，待法律审核。** 页面顶上写着"草案，待法律审核"。授权范围和期限、未成年人规则、运营方名称和联系方式都还是标黄的占位。
- 版本号有三处，必须一致，测试钉住：`crowd3d/records.py` 的 `TERMS_CURRENT`、`web/api.js` 的 `TERMS_VERSION`、两种语言协议上的 `data-terms-version`。
- 协议有实质变化就发新版本，上传前必须重新同意（D33 起：登记过的人同意一次新版本，昵称不变）。按旧版本上传的照片，公开的内容不超出那个版本允许的范围（`records.TERMS_VERSIONS` 列出现在仍然有效的版本）。D33 自己的修改没有发新版本，是上线前原地改的 `terms-v1`（见 [D33 的记录](D33-registration-fov.md)）。
- 首页和地标页底部链到协议，协议页本身也有两个切换。

**以前的数据：一次性迁移**（`Store._migrate_d32_terms`）：

- 打开数据库时，每张通过的照片记成按 `terms-v1` 同意，没通过的照片的同意清空。以前同意了 `share-location-v1` / `v2` 的、没同意的和撤回过的照片都一样处理：负责人说这些都是测试照片。
- 迁移和它的记录在同一个事务里：`meta` 表的 `migration.d32-terms` 记下时间、改成同意的张数、清空的张数和版本。所以它只跑一次，之后的撤回不会被重启改回去。有改动时日志里记一条警告。
- 在洗礼堂的真实数据副本上：51 张通过的照片都改成同意，`/poses` 公开 51 张、显示 39 张。
- D30 的"只公开位置"的同意（`share-location-v1` / `v2`）、"以前的照片一律不显示"的规则和上传时可选的勾选框都删掉了，钉住它们的测试也改了。
- **上线前要删掉这个迁移**，否则恢复一个 D32 之前的备份，会把里面所有照片悄悄算成同意。
- 迁移以后有照片的数据目录基本都有照片公开着，所以密钥对不上时服务一律拒绝启动（见 [USAGE.md](../USAGE.md) 的 `public_id.salt`）。

**照片接口**（`GET /api/landmarks/{id}/poses/{公开 id}/photo`，`photoposes.public_photo`）：

- 只按 12 位的公开 id 取，不收库内 id。只给此刻 `/poses` 里那一行的照片：通过、没撤回、在快照里、有确定的位姿。返回前再从库里读一次，确认它还公开着。
- 照片由处理图重新编码：只留 JFIF 头，没有 EXIF（GPS、时间、机型、焦距都没有）、注释、ICC、XMP 和 dpi。长边最多 1600 px，渐进式 JPEG，质量 80；洗礼堂 51 张中位 401 KB、最大 560 KB。处理图里还留着上传者写的 JPEG 注释，所以一定要重新编码，不能直接发处理图。
- 缓存：`Cache-Control: no-cache` 加弱 ETag `W/"<公开 id>.1"`。浏览器可以存着，但每次看都要问一次，所以撤回马上生效：带着旧 ETag 来问，撤回后也是 404。没有 `Last-Modified`，因为处理图的文件时间就是上传时间。
- 其余所有请求都得到同一个 404 `{"detail": "no such photo"}`，不带 ETag 和缓存头。包括：撤回的、没通过的、快照之后才上传的、没有位姿的照片，库内 id，别的地标的行，大写或长度不对的 id。
- 泄漏扫描也扫这个接口：每一行的照片字节里都没有库内 id、密钥、撤回凭证、昵称、服务器路径、文件名和 EXIF GPS；撤回的照片 404；照片的像素和这一行自己的处理图一致。
- 每次请求都重新编码（不缓存在服务器上）：洗礼堂的照片重新编码一张中位约 67 ms，整个请求中位约 105 ms；没有限流。

**照片和素模对照**（风格化查看器的"从这张照片的角度看"，`web/compare.js`）：

- 素模按这张照片的位置、朝向、俯仰、横滚和视角画，画面的宽高比和照片一样，照片放在旁边：宽屏并排，窄屏上下。
- "叠加"模式把照片盖在素模上，滑块调照片的浓淡（0–100%，步长 5），用来看两者对不对得上。
- ‹ › 和左右方向键按绕地标的顺序换照片，照片和素模一起换；Esc 返回总览，焦点回到卡片的按钮。
- 地址里带着 `view=<公开 id>` 和 `cmp`（`pair` 或 `overlay`，叠加时还有 `opacity`），所以换语言或分享链接都会回到同一个对照。选的模式和浓淡也存在本机。
- D30 的规则不变：只有测出了位置、高度、俯仰、横滚、视角和宽高比的行才和素模对照，不用假设的值画。EXIF 行（手机 GPS + 罗盘）和缺测量值的行只有"看照片"：单独显示照片，写明来源、2σ 范围和为什么不能对照。
- 位置的 2σ 范围超过 10 米时，提示"相机可能在这个范围里的任何地方，素模和照片可能对不上"。照片 404 时（例如刚被撤回）写"这张照片现在显示不了（可能已被撤回）"，素模照常显示。
- 在洗礼堂的真实数据副本上，1280 和 390 像素宽的屏幕都核对过：照片框和素模画面相差不到 0.9 px，叠加时完全重合。素模和照片大致对得上，偏差和这些照片至少 16 米的 2σ 范围相符。

**浅色 / 深色**：

- 每个页面（首页、地标页、用户协议、风格化查看器）都有"外观"：跟随系统 / 浅色 / 深色，默认跟随系统（`prefers-color-scheme`，系统一改马上跟着变）。
- 选了马上生效，不重新加载，存在本机。别的标签页和按"返回"回到的页面也跟着变。
- `web/boot.js` 是每个页面的第一个脚本，在页面画出来之前设好 `<html data-theme>`，所以不会先闪一下另一种颜色。颜色都是 CSS 变量，两种模式各一套。
- 正文文字的对比度在两种模式下都 ≥ 4.5:1（WCAG AA）：测试里有 26 对文字颜色，浏览器里实测最低 4.59（浅色模式的"失败"作业标签）。点云的标记和北向标志在两种背景上都 ≥ 3:1。Leaflet 的弹窗、缩放按钮和署名也跟着变。
- 风格化查看器：面板跟着浅色 / 深色变，素模、天空和画风不变。画风和浅色 / 深色互不相干。

**中文 / English**：

- 每个页面都有"语言"：跟随系统 / 中文 / English，默认跟随系统。规则是 `navigator.languages` 里第一个中文（zh 开头）或英文（en 开头）的条目说了算，都没有就用英文。
- 换语言会保存选择并重新加载页面，`<html lang>` 设成 `zh-CN` 或 `en`。浏览器禁用存储时，选择存在这个标签页里（`window.name`）。
- 风格化查看器的两个切换在面板里，对照时移到对照的工具栏里。所以模型加载中、加载失败、`ui=0` 时看不到切换，选择和别的页面共用。
- 页面上每一句话都有中英文两版（`web/strings.js`，由 `web/i18n.js` 查）。数字、日期和单位用 `Intl` 按语言格式化。
- 原有的中文文案抽出来时逐字保留（对比脚本核对过），例外只有几处：1,000 及以上的数现在统一加千分位（例如"用时 3,800 秒"）；服务器 5xx 错误有了自己的文案（"服务器出错了，请稍后重试（HTTP 500）"）；地图的缩放按钮写"放大 / 缩小"。英文按自然的英文写，不逐字翻。
- 服务器只发代码和英文的技术说明，不发中文。拒绝原因、警告、作业状态、作业错误、422 的字段错误、风格化模型的标签，都由网页按代码翻译；API 因此删掉了 `stylized.label`。原始的作业错误仍放在"技术信息"下面，不翻译；用户自己写的内容（地标名、昵称、文件名）也不翻译。
- 画风文件多了一块英文的名称和描述（`en`），校验器要求它是一行英文、不带中文。
- 测试保证：
  - 每条文案都有中英文，占位符相同；
  - 代码里用到的键都存在，每条文案都用到；
  - 英文模式下渲染出的首页、地标页、风格化查看器和对照里没有中文（浏览器里实测，整页只有语言选项里的"中文"）；
  - `web/` 下除了 `strings.js`，JS 和 HTML 里都没有中文；
  - API 的任何响应里都没有中文，用户自己写的内容除外。

**没有变的**：

- 取整（位置 1 米，朝向、俯仰、横滚 1°，视角 5°；视角后来由 D33 改成 1°）、快照、不显示粗糙位姿和扣下的规则（D30），`/poses` 的格式（第 2 版）。
- 照片资格（D31）；视觉定位仍关着。
- 重建输出：`RECON_OUTPUT_VERSION` 仍是 2。同意只决定别人看到什么，通过的照片产出的东西不变，`tests/test_recon_golden.py` 只多传了 `terms`（D33 起改成先登记一个上传者，见 [D33 的记录](D33-registration-fov.md)）。

**D32 时问产品负责人的两个问题**：

1. 视角取整到几度？**D33 已答复：1°**（"视角我之前就说了用一度"），已实现。
   - 决定里写"取整到 1 m / 1°"，而 D30 起视角取整到 5°，D32 时规则没改。
   - 照片公开以后，5° 挡不住什么（照片自己就看得出视角），却会让对照里的素模比例不准：视角 20° 时最多约 ±13%，10° 时约 ±25%。取整到 1° 时，这两个数是约 ±2.6% 和 ±5%。在佛罗伦萨洗礼堂的一份数据副本上（39 行），对照里素模比例的误差从最大 16.9%、中位数 3.7% 降到最大 2.9%、中位数 0.6%。
   - D32 时的默认是保持 5°。D33 改了 `crowd3d/photoposes.py` 的 `PUBLIC_FOV_STEP_DEG`（5 → 1）和几处文案。没有发新版本的协议：网站还没上线，没有真实用户同意过 `terms-v1`，所以直接改了 `terms-v1`；上线以后，任一语言有实质改动都要发新版本。
   - 版本号都不变：`/poses` 的格式仍是第 2 版（`rounding.fov_deg` 本来就写着取整的档），测试流程版本仍是 8（没有指标读 `hfov`），`RECON_OUTPUT_VERSION` 仍是 2（取整只在发出 `/poses` 和写基准记录时做，重建不用）。
2. 浏览器要不要记住"已同意"？**D33 已取代这个问题**（"用户协议在注册时即同意了"）：协议在登记时同意一次，这台设备记住登记，上传时不再勾选（见 [D33 的记录](D33-registration-fov.md)）。D32 时的两种做法：
   - 默认：不记。每次打开地标页勾选框都不勾，同一次浏览里继续上传不用再勾。
   - 另一种：这个浏览器记住同意过 `terms-v1`，版本没变就预先勾上。更顺手，但预先勾上的同意在法律上更弱。
