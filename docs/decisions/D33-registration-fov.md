# D33：用户协议在登记时同意一次、视角取整到 1°（2026-11-05）

> 原来是 README 的一节，D34 C 部分第 2 步（2026-11-13）搬到这里：文字没有改，只把指向 README 别的章节的话（"见上面某一节"）换成了链接。全部决定的索引在 [README.md](README.md)。

**产品负责人的决定**（原话："用户协议在注册时即同意了。视角我之前就说了用一度。"）。这是对 D32 两个问题的答复（见 [D32 的记录](D32-terms-compare-appearance.md)的最后）。

**开发这边的理解**（负责人可以改）：

- 原型没有账号：D32 时每次上传带一个随手填的昵称（`user_id`）和协议版本（`terms`），每次打开地标页都要先勾选同意协议才能上传。所以做一个最小的"上传者登记"：填昵称、同意现在版本的用户协议，服务器记下这次登记，发给浏览器一个保密的登记凭证。以后的上传都带这个凭证，不再每次勾选协议。
- 协议出了新版本时，登记过的人同意一次新版本就行，不用重新起昵称。
- 真正的账号（密码、邮箱）不在这次范围里，负责人要时再做。负责人说的是"注册"；因为没有账号，页面上叫"登记"。
- "一度"也包括视角：公开的视角从取整到 5° 改成 1°。

## 1. 用户协议在登记时同意一次

**地标页的上传卡片**：

- 没登记时，卡片只有登记表单：
  - 一句说明："第一次上传前，先登记昵称并同意《用户协议》。只需登记一次，这台设备会记住。"
  - 昵称（最多 64 个字符，会显示在共同完成者里）；
  - "我已阅读并同意《用户协议》"勾选框（链到协议），下面是它的说明（见下面"说明写明"）。
- 勾选框每次打开页面、每次切换表单都不勾。没勾就不发请求，提示"请先阅读并同意《用户协议》"，并把焦点放到勾选框上。没填昵称时提示填写。
- 登记以后，卡片显示"上传者昵称：<昵称>"和"忘记这台设备上的登记"按钮，下面是选照片和上传。D32 上传区里的勾选框没有了。
- 登记存在这台设备的 localStorage（`crowd3d.contributor`：凭证、昵称、同意的协议版本）。浏览器禁用存储时，登记只在这次浏览里有效，登记成功的提示后面会说"这台设备不能保存登记，刷新后需要重新登记"。
  - D32 时页面记住的昵称（`crowd3d.user_id`）会预先填进昵称框，登记以后删掉。
- 存下的协议版本不是现在的版本时，卡片换成"同意新版本"：上面仍是"已登记的昵称：<昵称>"和"忘记这台设备上的登记"按钮（不想同意新版本的人可以在这里忘掉登记），下面是一句说明"《用户协议》已更新……昵称不变"、勾选框和它的说明、"同意新版本"按钮。
- 上传被拒时：
  - `register_required`（服务器不认识这个凭证）：页面忘掉这份登记，回到登记表单，原来的昵称已经填好，提示"服务器上找不到这台设备的登记，请重新登记"；
  - `terms_outdated`：卡片换成"同意新版本"，提示"还没有上传：先同意新版《用户协议》，选好的照片会保留"（不重复卡片上的说明）。同意以后再点一次"上传"，选好的照片不用重选。
- "忘记这台设备上的登记"只删这台设备上的登记，不用确认。撤回凭证留着，照片仍可以在下面撤回。服务器上的登记不删（见下面的问题 2）。D34 第 2 步起页面会按登记向服务器查照片；忘记以后查不了，所以当时没列在页面上的照片就查不回来了（协议第 6 节写了）。
- 共同完成者里的"（你）"按登记的昵称标。
- 勾选框的说明写明（D32 的内容，D33 改了几处）：
  - 照片会公开，去掉 EXIF 等拍摄信息，长边缩到 1600 像素以内；
  - 拍摄位置（取整到 1 米）、朝向和视角（都取整到 1°）也公开，能确定位置和朝向的照片才显示；
  - 昵称出现在你有照片通过检查的地标的共同完成者里（只上传过、没有照片通过的地标不列），但不显示哪张照片是谁传的、什么时候传的；
  - 公开的照片要等下一次建模结束后才显示，但别人能让下一次建模很快开始，所以可能把新出现的照片和你的昵称对上；
  - 不同意就不能登记，也就不能上传；只需登记一次；上传后可以在这台设备上撤回照片。
- 在 Chromium 里，用洗礼堂真实数据的副本、真实的 API 核对过：中文、英文 × 浅色、深色 × 360、390、1280 px，共 12 种情况。
  - 三种卡片都切换对了，卡片和页面都没有溢出，英文页面上没有中文；
  - 凭证只出现在 POST 请求体里，地址里没有；上传的表单里没有 `user_id` 和 `terms`；
  - 旧昵称预先填进去、登记后删掉；同意新版本、忘记、服务器丢了登记这三条路都从头走到底。
  - 截图只留在仓库外。
- 之后又做了两轮截图检查（也是洗礼堂数据的副本、真实的 API，中文、英文 × 浅色、深色 × 1280 px 桌面、390 px 手机）。第 1 轮发现的问题在 aba2940 里改了：手机上的拍摄位置表加了边框和渐隐（下面第 3 部分的 (c)）、"同意新版本"的卡片也显示已登记的昵称和"忘记"按钮、`terms_outdated` 时的提示、存储被禁用时的提示、英文时间里的 PM 不单独换行、协议英文第 2 节的句子。第 2 轮在 aba2940 上：
  - 没有一项检查真的失败；两种外观的对比度检查都通过，英文页面上的中文只有语言选项里的"中文"；
  - 凭证扫描：22 个发出的凭证，对照 950 个请求、192 个响应、重新取的 79 个 GET（16.7 MB：页面、`/api`、`/poses`、照片、GLB）、23,444 段页面上看得见的文字、422 的响应体和服务日志，一次都没出现；数据库和 WAL 里有 18 个有效凭证的 SHA-256，没有凭证本身；
  - 发现两个小问题，当时没改，后来在 99b57e5 里改了（下面第 4 部分）。

**接口**（API 只发代码，页面按代码翻译，D32）：

- `POST /api/contributors`：`{nickname, terms}` → 201 `{nickname, terms, contributor_token}`，带 `Cache-Control: no-store`。
  - 先查协议版本：缺了或空着返回 422 `terms_required`，别的值返回 422 `terms_outdated`。
  - 再查昵称，用 D32 的 `user_id` 规则：去掉首尾空白后 1–64 个字符，不含控制字符，任何文字都行。也不能含落单的 UTF-16 代理项（JSON 的 `\ud800` 这类转义解出来的，不是字符，存不进库）。不合格返回 422（字段 `nickname`）。
  - 不合格时一行都不存。
  - 请求体由服务器自己读：只认 `Content-Type: application/json`、16 KiB 以内、顶层是对象的 JSON，别的都当作空的请求体（返回 `terms_required`）。协议版本被拒时 `input` 为 null，只回显文字的昵称（下面第 4 部分）。客户端没发完请求体就断开时返回 400 `the request body was cut off`（两个接口都是）。
- `POST /api/contributors/accept`：`{contributor_token, terms}` → `{nickname, terms}`，同意现在版本的协议。凭证缺了、不是字符串、格式不对或不认识返回 422 `register_required`；版本不对返回 `terms_required` / `terms_outdated`，这时登记记录不变。请求体的规则和登记一样，别的形状都当作空的请求体（返回 `register_required`）；422 的 `input` 一律为 null，不回显请求体里的任何内容。
- `POST /api/photos` 的表单现在是 `files`、`contributor_token`、`landmark_id`。凭证最先检查：
  - 缺了、空着、格式不对或不认识：422 `register_required`（`input` 为 null，不回显凭证）；
  - 登记时同意的版本不是现在的版本：422 `terms_outdated`（`ctx` 里是现在的版本和协议地址），要先 `accept`；
  - 这两项都在查文件数和地标之前，被拒时什么都不存、不排作业。
- 照片的昵称（`user_id`）和同意（`location_consent`）都取自登记记录。表单里另带的 `user_id`、`terms` 不读。
- 拒绝用 422 加类型码，不用 401 / 403：和 D32 的 `terms_*` 一样，页面走同一条翻译路径。
- `GET /api/contributors` 是 404：上传者的任何信息都不经 GET 给出。

**登记凭证**：

- 256 位随机数（`secrets.token_hex(32)`，64 位小写十六进制），只在登记成功时给这一次。
- 库里只存它的 SHA-256（`contributors.token_hash`，唯一）。不加盐，也不用公开 id 的密钥：凭证本身是 256 位随机数，没什么可猜的；公开 id 的密钥丢了，也不会让所有人的登记失效。
- 只放在 POST 请求体里（登记和同意是 JSON，上传是表单字段），从不放在地址或请求头里。开发这边对 D33 的理解允许请求头或表单字段；选了请求体，是为了不进日志。
- 任何 GET、点云、GLB、`/poses` 和公开的照片里都没有凭证、它的哈希和上传者 id（泄漏扫描查）；DEBUG 级别的日志里也没有凭证和它的哈希（日志测试查）。凭证字段没有格式约束，被拒时服务器自己写 422、`input` 为 null；登记和同意的请求体由服务器自己读，不交给 FastAPI 解析；上传接口的 422 一律不回显输入（`api.validation_error`；都见第 4 部分）。所以不管请求体是什么形状，这三个接口的 422 都不回显凭证。以前有两个例外：aba2940 时 `accept` 收到的凭证不是 JSON 字符串、或者请求体不是 JSON 时，FastAPI 自己的类型错误会把收到的值原样写回 422，99b57e5 改掉了；fc83755 时上传的凭证作为文件部分发来（凭证在文件名或这一部分的 Content-Type 里），或者凭证写在文本的 `files` 字段里，FastAPI 的 422 会把这一部分写回，ffe2a41 改掉了。
- 代价（设计时实测：在洗礼堂数据库的副本上，用设计的表结构直接写 SQLite，登记 1,000 次）：
  - 登记一次 0.40 ms；
  - 按哈希找凭证 8.7 µs（走唯一索引）；
  - 每次登记约 230 B（1,000 次多 229 KB）。

**记下什么、公开什么**：

- 新表 `contributors`：id、昵称、凭证的哈希、同意的协议版本和时间、登记时间。
- 照片多了一列 `contributor_id`：用哪个登记上传的，作为同意的来源记录，不公开。
- 昵称不唯一（和以前一样），两个人可以用同一个昵称（问题 1）。
- 共同完成者名单还是只有昵称，而且只列在这个地标有照片通过的昵称：只登记、没有照片通过的不出现。

**以前的数据：不迁移**：

- 打开旧数据库时加上 `contributors` 表和 `photos.contributor_id` 列。旧照片留着原来的 `user_id`，`contributor_id` 为空。
- D32 的一次性迁移照旧把它们算成同意 `terms-v1`。
- 评审在洗礼堂真实数据的副本上核对过：56 张照片的 `contributor_id` 都为空，`user_id` 不变。

**用户协议：直接改了 `terms-v1`**：

- D32 的规则是"协议有实质变化就发新版本"。D33 没有发新版本，而是原地改了 `terms-v1`：网站还没上线，没有真实用户同意过它。
- 改了的地方（中文、英文两版同样改）：
  - 第 1 节：登记时同意一次，不同意就不能登记，也就不能上传；
  - 第 2 节：只显示能确定位置和朝向的照片（下面第 3 部分的 (a)）；
  - 第 3 节：视角取整到 1°；
  - 第 4 节改成"登记和昵称"：登记本身不公开任何内容，有照片通过以后才在那个地标列出昵称；凭证存在这台设备的浏览器里，服务器只存它的指纹（哈希）；清了浏览器数据、换了设备或者"忘记"以后，要重新登记、再次同意；
  - 第 5 节：登记信息（凭证、登记时间、同意的时间）不公开；
  - 第 6 节：忘记登记不会删掉撤回凭证；
  - 第 10 节：出了新版本，登记过的人下次上传前同意一次，不用重新登记；
  - 页面的描述（meta description）。
- 版本号还是 `terms-v1`，三处一致，测试钉住。`crowd3d/records.py` 和 `web/terms.html` 的注释写明了这次原地修改。上线以后，任一语言有实质改动都要发新版本。

**基准和演示**：

- `scripts/eval_real_landmark.py` 的 `run_crowd`：建好地标以后、计时的上传请求之前，每个不同的伪用户经 `POST /api/contributors` 登记一次，再用它的凭证上传。昵称是去掉首尾空白的伪用户名。
  - 测试集里 408 个伪用户中有 2 个（commons-ten-v1）截到 64 个字符后以空格结尾，存下的昵称因此少一个空格；没有指标读昵称。
- `scripts/demo.py` 每位游客登记一次。
- 分数不变。测试里的合成众包场景，改动前后各跑一次：
  - 两种跑法：假重建器；真实 COLMAP 加风格化；
  - 整份运行摘要（143 个指标、逐张照片的记录、作业和模型）`diff` 完全相同，只去掉了时间、CPU、内存和随机 id；
  - COLMAP 那次限定一个建图线程：多线程的 COLMAP 拿同一份代码跑两次就有光束法平差的噪声（1,678 行不同），一个线程时两次基线完全相同；
  - 评审在提交后的代码上又跑了一遍，也相同。

## 2. 视角取整到 1°

- `crowd3d/photoposes.py` 的 `PUBLIC_FOV_STEP_DEG` 从 5 改成 1。`/poses` 里的 `hfov` 是整度，`rounding.fov_deg` 是 1。
- 对照里的素模用这个 1° 的值画（`web/compare.js` 读行里的 `hfov`，不用改）；素模上的图层收 1–150° 的视角。
- 在洗礼堂真实数据的副本上（39 行，35 行来自模型重建，4 行来自手机 GPS + 罗盘）：
  - 不同的视角值从 10 个变成 20 个；
  - 对照里素模比例的误差：最大从 16.9% 降到 2.9%，中位数从 3.7% 降到 0.6%。
- 隐私：视角取整得更细，透露镜头（焦距）的指纹也细了一点。但照片本身公开，从照片就看得出视角；协议第 7 节已经写明，取整只能限制数字本身透露的信息。
- 以前的结果：D33 之前记录的 11 个结果文件里，`public_fov_step_deg` 还是 5，不改（[docs/BENCHMARK.md](../BENCHMARK.md) 第 7.7 节）。

## 3. D32 留下的三个小问题

- **(a) 协议和标签说得比代码多**：
  - 问题：D32 时协议第 2 节和这里都写"每张通过的照片都公开"。可是第 3 节和代码只显示确定了位置和朝向的照片：`/poses` 只列这些行，照片接口只给这些行的照片。
  - 改法：协议第 2 节、"公开的拍摄位置"表的说明和登记说明都写明，只显示能确定位置和朝向的照片。上传结果的标签从"下次建模后公开（可撤回）"改成"确定了位置和朝向后公开，最早在下次建模结束后（可撤回）"。
- **(b) 中文的上传摘要多了一个西文空格**：
  - 问题：两句中文之间夹着一个西文空格。
  - 改法：两句改用 `common.sentenceSep` 连接（中文为空，英文是一个空格），现在是"1 张通过，1 张未通过。已开始生成：东北立面、完整模型。"。
- **(c) 手机上"公开的拍摄位置"表看不全**：
  - 问题：390 px 宽时，英文的"位置"一列被截在半中间；朝向和 ±范围两列在两种语言里都要横着滚动才看得到，页面上又没有提示。
  - 改法：表格外框窄于 640 px 时，每行竖排，值前写列名。
  - 这里按卡片的宽度判断（CSS 容器查询，容器是这张卡片 `#poses-card`），不按屏幕：700–1024 px 宽的屏幕上主栏也只有 258–582 px。640 px 是最宽的表（英文、EXIF 行带"你的"标记）要的 616 px 加一点余量（加了边框以后是 632 px，见第 4 部分）。
  - 列名用 `data-label` 写在格子前面，不进读屏读的名字。表格加了明确的 ARIA 角色，竖排时读屏仍按表格读。
  - 竖排的一行有 80–150 px 高，D30 的 360 px 滚动框只放得下三四行；手机的滚动条又浮在内容上、平时看不见，被截断的那一行看起来像下面说明的标题（第 1 轮截图检查发现）。所以窄卡片上滚动框加了 1 px 的边框，底边加一道渐隐（`position: sticky`，贴着框的底边）盖住被截断的那一行；滚到底、或者整张表放得下时，渐隐落在最后一行下面的空白上（aba2940；99b57e5 起每种宽度都有，见第 4 部分）。
  - 核对（洗礼堂数据副本，39 行）：中文、英文 × 浅色、深色 × 320–1280 px 共 40 种情况，都没有横向滚动，也没有被截断的格子；列名对比度浅色 5.79:1、深色 6.79:1。第 2 轮截图检查在 aba2940 上又跑了这 40 种，另加 40 种带"你的"标记的，都通过：窄于 640 px 时有边框，渐隐在框的底边，滚到底时不盖住最后一行；1280 px 时仍是表格。
  - 不支持容器查询的旧浏览器还是表格，要横着滚动。

## 4. 最后几个小问题（评审和第 2 轮截图检查之后）

## 版本号为什么都不变

- **`RECON_OUTPUT_VERSION` 仍是 2**：
  - 规则是任何可能改变重建输出（稀疏模型、PLY、模型 JSON、质量门结论）的改动都要升版本，改 ingest 也算。
  - D33 改了 ingest，但只改了昵称和同意从哪儿来。重建的代码（`coverage`、`jobs`、`reconstruct`、`validation`、`qa`）不读 `user_id`、`location_consent` 和 `contributor_id`。grep 只找到 `jobs.py` 为视觉定位作业引入 `location_shared`，那个作业只用于显示，不进重建。视角的取整只在发出 `/poses` 和写基准记录时做。
  - `tests/test_recon_golden.py` 不重新生成就通过。它现在先经 `crowd3d.contributors` 登记一个上传者；这个模块自己 import `uuid`，所以测试替换掉的 ingest 的 `uuid` 照样给出原来的照片 id。
