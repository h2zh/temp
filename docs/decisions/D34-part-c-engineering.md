### 1. 依赖文件

**哪里不对**：

- 只有一个 `requirements.txt`，10 个包。`scripts/` 和测试要用的 pyarrow 不在里面：干净环境照 README 安装后，`tests/test_materialize_testset.py` 有 9 个测试报错。
- `crowd3d/` 直接导入了 starlette、pydantic 和 anyio，清单里没有，版本由 FastAPI 带进来的是哪个算哪个。
- 运行服务用不到的 pytest 和 httpx 和运行依赖混在一起。
- 没有锁文件：间接依赖换了版本，谁也看不出来。

**改了什么**：拆成三层，每一层用 `-r` 包含下面一层，每个包都写成 `名字==版本`，版本就是仓库 `.venv` 里装着的那个。

| 文件 | 给谁用 | 自己列的包 |
|---|---|---|
| `requirements.txt` | 只运行服务 | numpy、opencv-python-headless、pycolmap、fastapi、starlette、pydantic、anyio、uvicorn、python-multipart、piexif、pillow |
| `requirements-eval.txt` | 再加上 `scripts/` 和评测 | httpx、pyarrow |
| `requirements-dev.txt` | 再加上测试和检查（开发、CI 装这个） | pytest、pytest-xdist、ruff |
| `requirements-lock.txt` | 约束文件（`pip install … -c requirements-lock.txt`） | 干净环境的 `pip freeze`，32 个包：上面 16 个，加上它们带进来的 16 个 |

新增的版本：starlette 1.9.0、pydantic 2.14.1、anyio 4.15.1（原来就装着，只是没写）、pyarrow 26.0.0（同上）、pytest-xdist 3.8.0、ruff 0.17.4（这两个是这一步新装进 `.venv` 的，pytest-xdist 带进来 execnet 2.1.2）。原有 10 个包的版本一个没动。

**导入是怎么找的**：`tests/test_tooling.py` 用 Python 的 `ast` 把三个目录的每个 `.py` 文件走一遍：`import` 和 `from … import`（函数里面的也算），以及参数是字符串的 `__import__`、`import_module`、`importorskip`；去掉标准库和仓库自己的模块，再用 `importlib.metadata.packages_distributions()` 把模块名换成包名（`PIL` → pillow，`cv2` → opencv-python-headless）。扫出来的结果：

| 目录 | 直接导入的第三方包 |
|---|---|
| `crowd3d/` | pillow、anyio、opencv-python-headless、fastapi、numpy、piexif、pycolmap、pydantic、starlette、uvicorn |
| `scripts/` | pillow、opencv-python-headless、fastapi、httpx、numpy、pyarrow、pycolmap |
| `tests/` | pillow、anyio、opencv-python-headless、fastapi、numpy、piexif、pyarrow、pycolmap、pytest、uvicorn |

有三个包没有任何文件导入，但是要装，测试里各写了一句理由：python-multipart（FastAPI 读上传表单要用，没有它 `create_app` 直接抛 `RuntimeError`，实测过）、pytest-xdist（`pytest -n`）、ruff。

**不让它再走样**：`tests/test_tooling.py` 里 23 个快速测试，其中管依赖的 22 个：

- 每个目录导入的第三方包都钉在它那一层的文件里（或者那个文件包含的文件里）；
- 反过来，文件里列的每个包，它那一层确实有文件导入（上面三个例外除外）；
- 每一行都是 `名字==版本`，同一个包不在两层里各钉一次；
- 钉的 16 个包，装着的版本就是钉的版本（一个包一个测试；没装的包是跳过，不是失败，因为不少测试本来就允许没有 pycolmap）；
- 锁文件里这 16 个包的版本和三个文件一致，并且每一行都是 `名字==版本`。

拿 9 种改坏的写法试过，每一种都有测试失败：从 `requirements-eval.txt` 删掉 pyarrow、从 `requirements.txt` 删掉 starlette、把 anyio 从服务那一层挪到开发那一层、往 `requirements.txt` 加一个没人导入的 click、把 numpy 钉成另一个版本、把 `==` 写成 `>=`、锁文件里 fastapi 的版本不一样、锁文件里没有 ruff、往 `scripts/` 加一个导入 yaml 的文件。

**锁文件是怎么来的**：在一个全新的虚拟环境里 `pip install -r requirements-dev.txt`，用仓库 `.venv` 的 `pip freeze` 当约束，装完的 `pip freeze` 和仓库 `.venv` 的逐行相同（32 行）。也就是说，三套测试一直在跑的那个环境，现在原样写进了 `requirements-lock.txt`。锁文件没有哈希（见"这一步没做的"）。

**在干净环境里验证**：一个全新的虚拟环境（`python3.13 -m venv`），照 README 写的那一行安装（`pip install -r requirements-dev.txt -c requirements-lock.txt`；包已经在本机的 pip 缓存里时约 10 秒）。装完的 `pip freeze` 和锁文件逐行相同（32 行）。在这个环境里快速测试 1,420 个全部通过、慢测试 40 个全部通过，数量和仓库的 `.venv` 里一样。包索引是通过本机配置的代理访问的，TLS 校验没有关。验证完这个环境就删掉了。

### 3. 并行运行

**哪里不对**：`.venv` 里没有 pytest-xdist，4 个核只用 1 个。

**改了什么**：pytest-xdist 加进 `requirements-dev.txt`；找出并行时会互相影响的测试，改掉。推荐的写法是 `python -m pytest -q -m "not slow" -n 4`。

#### 找到的三处共享状态

先拿改之前的测试直接用 `-n 4` 跑，再拿一个记录"哪个测试之后进程的内存分配器被钉住"的临时插件跑了一遍，又在 8 个空转进程占着 4 个核的情况下把带时间断言的几个文件跑了一遍。找到三处，都改了：

**(a) 测试进程的内存分配器被别的测试钉住。** 服务启动时会给自己所在的进程钉住 glibc 的 mmap 阈值（`ingest.pin_malloc_threshold`，D34 第 1 步），钉了就改不回去。`conftest.py` 的 `settings` 夹具把这个开关关了，但自己造 `Settings` 的代码没有关：快速测试里是评测工具（`tests/test_benchmark.py` 2 个测试、`tests/test_eval_real.py` 6 个测试通过 `run_crowd` / `rescore` 在测试进程里用默认设置启动服务），慢测试里是端到端的几个模块级夹具（`test_e2e.py`、`test_e2e_stylize.py`、`test_localize.py`）。同一个进程里排在它们后面的所有测试都在钉住的分配器上跑；哪些测试受影响取决于运行顺序，并行时还取决于分到哪个进程。

改法：`conftest.py` 加两个对所有测试自动生效的夹具。

- `server_starts_leave_the_allocator_alone`（整个会话一个）：测试进程里，服务启动时的那次调用什么都不做。它必须是会话级的：模块级夹具启动服务的时候，测试自己的夹具还没建起来（第一版写成了每个测试一个，读慢测试的夹具时发现挡不住它们，改了）。
- `the_test_process_keeps_its_allocator`（每个测试一个）：测试结束时如果进程被钉住了，这个测试自己失败，而不是让后面的测试换一个环境跑。

钉住分配器这件事本身照旧有测试：`tests/test_ingest.py` 用一个记录调用的假 C 库测逻辑，`tests/test_api.py` 的三个真实服务进程测效果（那是子进程，不受夹具影响）。新加的测试 `test_a_server_started_inside_a_test_leaves_the_allocator_of_the_test_process_alone` 守着第一个夹具：去掉它，这个测试就失败。

**(b) 真实服务进程的端口。** `tests/test_api.py` 的 3 个测试和 `tests/test_gzipfiles.py` 的 1 个测试各启动一个真实的服务进程。原来的做法是先向内核要一个空闲端口、关掉、再把端口号交给服务；关掉和服务绑定之间有空当，两个测试进程同时这么做时可能拿到同一个端口，之后一个测试会和另一个测试的服务说话。概率很小（两次取端口要正好撞上同一个号），但并行以后是真的可能。

改法：新文件 `tests/server_process.py`，服务用 `--port 0` 启动，由内核在绑定时分配端口，测试从 uvicorn 的启动日志里读出端口号。两个文件原来各有一份几乎相同的启动代码，现在共用这一份。服务端代码没有改。

**(c) 一个按墙上时钟计时的断言余量太小。** `tests/test_geo_exif.py::test_a_header_flood_is_unreadable_before_pillow_sees_it` 断言"拒绝一个 24 MB 的坏文件头用时不到 0.5 秒"，计时用的是墙上时钟。最慢的三种文件在空闲的机器上就要 0.2–0.36 秒，机器一忙就超：第一次 `-n 4` 就失败了 1 个，8 个空转进程时失败 3 个。

第一次的改法是把这个文件里量"一次调用花多少"的函数 `cost_of` 改成量本进程的 CPU 时间（`time.process_time`），0.5 秒的界线不动。被量的调用只解析内存里的字节，不等任何东西，所以机器空闲时两种时间是同一个数；机器忙时墙上时钟把别的进程也算进去了（8 个空转进程占着 4 个核时，墙上时钟 1.27–1.49 s，CPU 时间 0.31–0.32 s）。

**这个改法不够**：它挡住了"机器忙"，没有挡住"机器慢"。CI 在 GitHub 上的第一次运行就在这一条上失败了（0.555 s）。现在的写法（不带内存记录计时，界线按同一个进程里现量的一段参照工作来定）和全部按时间设的界线的清单见第 6 节；内存峰值取自哪一次调用见第 7 节。

量 CPU 时间这一点留下了。代价是这个断言不再能发现"调用在等待而不是在计算"这一类变慢；被量的函数（`read_photo_meta`、`_read_exif`）不做读写、不拿锁，没有可等的东西。

#### 查过、不用改的

- 测试写文件都在 `tmp_path` 里；整套快速测试跑完，仓库目录里除了缓存目录（`.pytest_cache`、`__pycache__`）没有新文件。
- 环境变量、`PIL.Image.MAX_IMAGE_PIXELS`、模块里的常量都是用 `monkeypatch` 改的，测试结束自动还原。
- 模块级的缓存（`structure_pipeline._LOADED`、`subject._memory`、`jobs` 和 `synthetic` 的 `lru_cache`、`params` 的当前参数）每个进程一份，并行时互不相干；同一个进程里换顺序是否有影响，由下面的"换顺序"检查。
- 会话级夹具 `synthetic_dataset`（生成合成照片，约 3 秒）每个进程各建一次。
- `tests/test_e2e.py` 的真实 uvicorn 用的就是端口 0（它是慢测试，不并行）。
- 其余按墙上时钟计时的断言在 8 个空转进程占着 4 个核时全部通过。当时只凭这一点就写了"余量够"；评审第 1 轮之后逐条量了实测值和余量，清单在第 6 节。

没有用到 `xdist_group` 和 `--dist loadgroup`：三处都改成了各用各的，没有哪个测试必须留在同一个进程里。

**这份清单当时漏了一处**：真实服务进程上"请求体后到"的那个测试，结果取决于测试进程被调度得快不快。它和共享状态无关，单进程时也有，只是并行以后 CPU 一紧就露出来（评审的 10 次 `-n 4` 里失败了 1 次）。见第 6 节。

#### 两个已知偶尔失败的测试

**(i) `tests/test_api.py` 里"不是这个地标的行就一律 404"的列表。** 列表里有 `row_id.upper()`。公开 id 是 12 位十六进制，恰好不含字母时（(10/16)¹² ≈ 0.36%，约 280 次里 1 次）大写和原来是同一个 id，于是测试拿一个有效的 id 去期待 404。

- 复现：一个临时插件把每个公开 id 里的 a–f 换成 0–5，这个测试必然失败（200 而不是 404）。
- 改法：列表里放的是这个地标所有带字母的行的大写形式；一行都不带字母时这一项为空（那时本来就没有"只差大小写"的 id）。原来只试第一行，现在每一行都试。
- 验证：同一个插件下通过；不带插件通过；把照片接口改成不分大小写（变异），测试失败。

`tests/test_api.py` 里另有 4 处把凭证转成大写再发出去，对象是 64 位十六进制的凭证，不含字母的机会是 (10/16)⁶⁴ ≈ 10⁻¹³，没有动。

**(ii) `test_the_server_pins_the_malloc_threshold_when_it_starts`。** 它最后断言"没有哪个测试钉住过这个进程"。按文件名顺序跑时 `test_api.py` 排在 `test_benchmark.py` 前面，所以一直通过；先跑 `test_benchmark.py` 或 `test_eval_real.py` 就失败。

- 复现：`pytest tests/test_benchmark.py tests/test_api.py::test_the_server_pins_the_malloc_threshold_when_it_starts`，1 个失败（`assert 4194304 is None`）。
- 改法：就是上面的 (a)。这个测试本身一个字没改，它断言的那句话现在是真的。
- 验证：`test_benchmark.py`、`test_eval_real.py`、这个测试、`test_ingest.py` 按这个顺序一起跑，216 个全部通过。

#### 换顺序

整套快速测试按三种别的顺序各跑了一遍，都是单进程：

| 顺序 | 结果 | 用时 |
|---|---|---|
| 测试文件按名字倒着排（文件里的顺序不变） | 1,420 个通过 | 302.5 s |
| 整个列表倒过来（文件倒着排，文件里的测试也倒着排） | 1,420 个通过 | 298.2 s |
| 文件的顺序和每个文件里测试的顺序都打乱（固定的随机种子 20261112） | 1,420 个通过 | 303.0 s |

改之前（574f4c3 的导出），文件倒着排时因为顺序而失败的只有上面的 (ii)（那次运行里还有 1 个失败和顺序无关：`test_code_fingerprint_covers_the_code_a_run_executes` 要求代码树是 git 检出，单独跑它在导出的目录里也失败）。改之后没有发现别的顺序依赖。后两种顺序用的是一个只为这次检查写的临时插件，没有进仓库。

#### 实测：单进程和 4 个进程

用时是 pytest 自己报的秒数。跑的时候机器上没有 COLMAP，也没有别的测试。

| 写法 | 结果 | 用时 |
|---|---|---|
| 单进程（基准），3 次 | 每次 1,420 个通过 | 303.6 s、302.9 s、303.7 s（约 5 分 4 秒） |
| `-n 4`，3 次 | 每次 1,420 个通过 | 88.5 s、88.3 s、89.8 s（约 1 分 29 秒） |
| `-n 2` | 1,420 个通过 | 158.2 s |
| `-n auto`（本机就是 4 个进程） | 1,420 个通过 | 88.0 s |
| `-n 8`（进程数是核数的两倍，看余量） | 1,420 个通过 | 93.1 s |
| `-n 4 --dist loadfile`（一个文件的测试留在一个进程里） | 1,420 个通过 | 96.1 s |
| `-n 4 --dist worksteal` | 1,420 个通过 | 87.7 s |

4 个进程比单进程快 3.4 倍（中位数 303.6 s 对 88.5 s）。到不了 4 倍，是因为每个进程都要各自导入代码、各建一次合成照片和用到的模块级场景。默认的分发方式和 `worksteal` 差不多；`loadfile` 慢一些（最大的几个文件各占住一个进程）。所以推荐的写法不带 `--dist`。

上表里的 8 次并行运行全部通过；改之前第一次 `-n 4` 就有 1 个失败（上面的 (c)）。8 次不足以说"可靠"：评审把 `-n 4` 又跑了 10 次，失败 1 次。那个测试改掉之后重新跑的次数和结果见第 6 节。

#### `-n` 不写进 `addopts`

不写。理由：

- 单进程的写法是基准，必须照旧能用，而且不依赖 pytest-xdist 装没装（写进 `addopts` 以后，没装 xdist 的环境里 `pytest` 直接报"不认识的参数"）。
- 慢测试跑真实的 COLMAP，必须一个一个跑；写进 `addopts` 就得每次记着加 `-n 0`。
- 调试时要 `-s`、`--pdb`，这两个在并行时用不了。

所以并行是明写的：README 的命令和 CI 里各写一次。

#### (一) CI 的第一次运行失败：拒绝坏文件头"不到 0.5 秒"

**现象**：工作流文件推上去以后的第一次运行（GitHub 的 run 43285497995，`ubuntu-24.04`，Python 3.13.18，`-n auto`）：1,419 个通过，1 个失败。

```
tests/test_geo_exif.py::test_a_header_flood_is_unreadable_before_pillow_sees_it[png: empty pixel data chunks]
assert seconds < 0.5 and peak < 256 * 1024, (0.5552008280000109, 1701)
```

`fast` 任务停在这一步，后面单独跑 node 测试的那一步没有执行。（node 测试其实跑过了：`tests/test_web.py` 在 pytest 里跑同一批 `web/tests/*.test.mjs`，它在通过的 1,419 个里。）

**原因有两层**：

1. 界线是一个绝对的秒数，量的东西却跟着机器的快慢走。这一步前面把计时从墙上时钟改成了 CPU 时间，界线没动；这个参数在开发机上单独跑是 0.30–0.35 s，在整套测试里是 0.37 s，余量只有 1.3–1.7 倍。本文原来写的"本机最慢 0.31 s，1.6 倍余量"偏乐观，而且 1.6 倍本来就不够。GitHub 的机器慢一些，就超了。
2. 量出来的时间里，约 95% 不是"拒绝这个文件"花的，而是 `tracemalloc` 记录每一次内存分配的开销：`cost_of` 先打开 `tracemalloc`，再读时钟。同一次调用，不开记录是 0.017 s，开着是 0.30 s。23 种坏文件头里，开着记录比不开慢 6–24 倍（只有一种几乎不分配内存的例外，1.1 倍）。所以原来那条断言量的主要是记录工具有多快。

| 拒绝 2,000,000 个空的 PNG 数据块（24 MB），本进程 CPU 时间 | 开着 `tracemalloc` | 不开 |
|---|---|---|
| 开发机，单独跑 5 次 | 0.296–0.350 s | 0.0166–0.0177 s |
| GitHub 的机器，CI 里那一次 | 0.555 s | （没有量过） |

**改了什么**（只有 `tests/test_geo_exif.py`）：

- **时间不带记录量。** `cost_of` 一共调 4 次：第 1 次开着 `tracemalloc`，只取内存峰值；后 3 次不开，取最小的 CPU 时间。带记录那一次的结果必须和后面的一样（比较 `repr`），否则测试失败。（这一轮当时提交的顺序是反的：先计时 3 次，第 4 次才带记录取峰值。那样峰值量的是"已经调过 3 次以后"的调用，评审第 2 轮指出这是把内存那一半的断言放宽了；现在的顺序和原因见第 7 节。）
- **时间的单位是"一趟"，不是秒。** 新函数 `walk()` 在同一个进程里现量一段固定的解释器工作：在一块缓冲区上走 65,536 步，每步切两片、读一个整数（和被测的文件头检查是同一类工作）。量 5 次取最小，每个进程量一次；开发机上一趟约 0.012 s。`cost_of` 返回的时间是"几趟"。机器慢一倍，这一趟也慢一倍，比值不变。
- **界线换算成趟数。** 原来 0.5 秒的写成 40 趟，1.0 秒的 80 趟，0.1 秒的 8 趟。开发机上一趟是 0.011–0.013 s，所以 40 趟是 0.42–0.50 s：和原来的秒数相当，没有放宽；而被量的时间因为不带记录，比原来小了一个数量级。
- **坏文件头那一条收紧到 10 趟**（开发机上 0.12 s；原来是开着记录 0.5 s）。理由在下面的"变异"里：计时不带记录以后，0.5 秒已经拦不住"把整个文件读完才拒绝"这种写法。
- `test_what_the_limits_let_through_costs_milliseconds` 原来自己带一个不开记录的计时函数（墙上时钟，3 次取最小，< 0.5 s）。`cost_of` 现在量的就是这个，所以改用 `cost_of`，界线 40 趟。

#### (二) `-n 4` 十次里失败一次：真实服务进程上"请求体后到"的测试

**现象**：评审把 `-n 4` 连跑 10 次，第 1 次失败：

```
tests/test_api.py::test_a_real_server_sends_the_file_whole_when_the_body_passes_the_limit_after_the_answer_began
AssertionError: ('/files/models/demo/m.glb', 200, 98304, 1048580)
```

1 MiB 的模型文件只收到 98,304 字节。这个测试单独跑、旁边放 4 个空转进程：40 次里失败 1 次；在 574f4c3 上同样跑，40 次里失败 6 次（都是评审测的）。所以毛病在这一步之前就有，并行以后 CPU 一紧才露出来。

**原因**：这个测试先发请求头，等收到回答的响应头，再发一个超过上限的请求体（"后到"），然后断言文件完整。它成立有一个没写出来的前提：请求体到的时候，服务器还在发文件。

- 文件只有 1 MiB 左右时，服务器不用等客户端读，就能把整个文件交给内核（回环连接上内核的发送缓冲区有几 MiB），然后关闭连接。
- 测试进程从收到响应头到发出请求体，中间只要被耽搁几十毫秒，请求体到的就是一个已经关闭的连接。内核对这种数据的回答是复位连接，服务器那一侧还没送达的文件内容随之丢掉。客户端读到已经送达的那一截（98,304 或 128,000 字节），然后是"连接被复位"。（这一条是按 TCP 的规矩推出来的，没有抓包；下面量到的现象都和它一致。）
- 服务器日志里没有任何错误：从应用的角度看，它已经把文件完整地发完了。

确定地复现：一个临时插件让"后到"的请求体晚发 0.05 秒，897f04e 上的测试每次都失败（`three.module.js` 只收到 98,304 / 1,272,972 字节）。

**量了一下，多大的文件服务器"交不完"**（真实服务进程，请求体在响应头之后 0.3 秒才发；本机内核的 `net.ipv4.tcp_wmem` 第三个数是 4 MiB，这是默认值）：

| 文件 | 请求体紧跟着发 | 请求体晚 0.3 秒发 |
|---|---|---|
| 首页 `/`（4,350 字节）、`/style.css`（29,203 字节） | 完整 | 完整 |
| `three.module.js`（1.27 MB） | 完整 | 只有 128,000 字节，连接被复位 |
| 模型 1、2、3 MiB | 完整 | 只有 128,000 字节，连接被复位 |
| 模型 4、5、6、8、12、16、64 MiB | 完整 | 完整 |

所以有三种文件：

- **比连接装得下的还大**（本机 4 MiB 起）：请求体什么时候到，服务器都还在发。这正是 A 部分那个修改管的情形，文件必须完整。
- **很小**（几 KB 到几十 KB）：在请求体能发回来之前，内核已经把整个回答送到了，所以也总是完整，不管服务器那时还在读请求体还是已经关了。
- **中间的**（`three.module.js`、1–3 MiB 的模型）：看谁快。服务器还在发就是完整的；已经发完关掉了，就被复位截断。

**改了什么**（只有 `tests/test_api.py`）：

- 模型文件从 1 MiB 改成 16 MiB：`more_than_a_connection_holds()` 读内核的 `tcp_wmem` 上限，取它的 4 倍（读不到时按 4 MiB 算）。客户端这一侧的接收缓冲区固定成 64 KiB，内核不会自己把它调大。这样服务器在客户端不读的时候最多交出去 4 MiB 多一点，剩下 11 MiB 以上只能等着。
- 对这个模型，"后到"的 4 次请求照旧断言文件完整；另加 1 次：请求体在响应头之后 0.3 秒才发，文件也必须完整。
- 首页照旧断言完整（测试里顺便断言了它小于 32 KiB，将来首页长大了，这里会先提醒）。
- `three.module.js` 的 4 次"后到"请求照旧发，状态码照旧必须是 200；内容的断言改成：完整，或者连接被复位、收到的是文件开头的一截。别的情况（没被复位却不完整、内容不对）仍然失败。它是仓库里的固定文件，没法换成大的。
- "一起发"的 12 次请求、最后对服务器日志的两条断言（8 条 `three.module.js` 的请求行；没有 `ERROR`、`Exception`、`Traceback`）都没有变。
- 辅助函数 `get_with_a_chunked_body` 多返回一个"连接有没有被复位"，多一个"晚多久再发"的参数；它的说明原来写"服务器在复位之前回答的内容仍然读得到"，这句话在上面那种情况下不成立，改掉了。

### 7. 评审第 2 轮之后改的一处：`cost_of` 量的是第一次调用

评审第 6 节 (一) 的改法时又发现一个问题，属实，改了。只动了 `tests/test_geo_exif.py`：函数 `cost_of`，外加三处注释里的实测值。`crowd3d/` 和 `scripts/` 一个字节没动。

**哪里不对**：改之前（574f4c3）`cost_of` 只调用一次，开着 `tracemalloc`，时间和内存峰值都来自这一次——它是这些字节在进程里的第一次调用。第 6 节 (一) 为了让计时不带内存记录，改成了"先不带记录调 3 次计时，再带记录调第 4 次取峰值"。这样一来，峰值量的是第 4 次调用：前 3 次已经把进程里的缓存填好了，第一次调用留在缓存里的东西不再算进去。

而这些测试守的那个发现，本身就是一笔"留在缓存里"的开销：`piexif` 按 EXIF 里声明的个数拼一个 `struct` 格式串，一个值一个字符；`struct` 模块把编译好的格式存进自己的缓存，每个字符 33 字节（`crowd3d/exif.py` 里 `_tiff_value` 的说明）。同样的字节再读第二次，格式已经在缓存里，几乎不花什么。对服务器来说每一次上传都是"第一次"。

所以那一改是把断言放宽了，而上一轮的记录和报告里都没有说（只说了 `three.module.js` 那一处）。

**时间那一半是同一个毛病**，评审没有列，是复现的时候量出来的：3 次里取最小，取到的总是后面的调用，第一次调用的时间同样被丢掉了。（评审的建议里写"时间反正都是三次里最小的，界线不用动"。界线确实不用动；但改之前的时间是第一次调用的时间。）

**复现**（改坏的都是 `crowd3d/exif.py` 的临时拷贝，仓库里的文件没有动）：

**改了什么**（`cost_of`，一共还是调 4 次）：

- **带记录的那一次放回第一个。** 峰值来自第 1 次调用；它留在进程里任何缓存中的东西都算进去。后 3 次不带记录，取最小的 CPU 时间。带记录那一次的结果仍然必须和后面的相同（比较 `repr`）。
- **每次调用之前清空 `struct` 模块的格式缓存**（`struct._clearcache()`，在计时和内存记录之外做）。这一条评审的建议里没有，是这里加的，理由有两个：

### 8. 收尾跑测试时遇到的一个偶发失败：峰值内存"不低于"作业前的内存

第 7 节的修改做完，在要提交的代码树上跑最后一遍测试时，`-n 2` 那一遍失败了 1 个（其余 1,419 个通过；同一棵树上单进程、`-n 4` 三遍、`-n auto`、慢测试都全部通过）：

```
tests/test_eval_real.py::test_run_crowd_end_to_end_with_the_fake_reconstructor
assert m["peak_rss_jobs_mb"] >= m["baseline_rss_mb"]        380.7 对 381.1
```

这个测试文件这一轮没有动过。这条断言和它量的那段评测工具代码是 2026-10-29（84db9a1）加的，比 C 部分早。这一轮里旧断言随整套快速测试一共跑过 10 遍，失败这 1 遍；评审第 1 轮之后在提交的代码树上跑的 20 多遍里没有失败过。

**负责人 2026-11-13 的裁定**：C 部分不动 `scripts/`，在测试这一边改。这条断言要求的精度内核并不保证；只放开记账上的那点出入，不多放，界线要有出处；断言变松了，要在"和任务说明不一样的地方"里明说；评测工具报的峰值可能比作业前的内存低这么多，记作留给以后的事。

**两个数是什么**（`scripts/eval_real_landmark.py` 的 `run_crowd`）：一次上传请求的照片被接受之后，评测工具先读 `/proc/self/status` 的 `VmRSS`（进程现在的常驻内存），这是 `baseline_rss_mb`，作业前的内存；接着往 `/proc/self/clear_refs` 写 5，把 `VmHWM`（常驻内存的最高记录）复位；然后跑作业；跑完读 `VmHWM`，这是 `peak_rss_jobs_mb`。两个数各自四舍五入到 0.1 MB。一次运行报的是峰值最高的那次请求的这两个数。

这个测试用的是假的重建器，作业几乎不占内存。所以两个数量的其实是同一块内存，谁大谁小由内核怎么记账决定。

**内核的规则**（读的是 Linux v6.18 的源码：`fs/proc/task_mmu.c`、`include/linux/mm.h`、`lib/percpu_counter.c`；开发机的内核是 6.18.44）：

- 一个进程的常驻页数记在三个计数器里：文件页、匿名页、共享内存页。为了快，每个处理器对每个计数器各有一个"零头"：页数的增减先记在零头里，零头攒到 `max(32, 2 × 处理器数)` 页才并进总数。
- `VmRSS` 是精确值：总数加上所有处理器的零头。6.16 起是这样；6.15 及以前读的是不含零头的总数（对过 6.1、6.2、6.12、6.15、6.16、6.17 的 `task_mmu.c`）。
- `VmHWM` 是"现在的精确值"和"记下的最高值"里大的那个。记下的最高值只在两个时候更新：复位的时候，和常驻内存将要下降之前。两处用的都是**不含零头**的总数。
- 所以，复位之后内存如果只降不升，读到的 `VmHWM` 就是复位时不含零头的总数。它比复位前读到的 `VmRSS` 少的，正是当时各个处理器零头的和。
- 一个零头最多 31 页（到 32 页就并进总数了）。所以最多少 3 个计数器 × 处理器数 × 31 页：4 个处理器、4 KB 的页，是 372 页，1,488 KB。
- 6.15 及以前两个数是同一种读法，没有这个出入。

`/proc/self/stat` 的第 24 项（rss）读的就是不含零头的总数，所以这条规则可以在开发机上直接对出来。

**在哪台机器上量的**：这一节做到一半时容器重启过，换了一台机器：仍是 4 核，处理器是 Intel Xeon 2.10 GHz（之前是 2.3 GHz），内核 6.18.44。下表里"这个测试单独跑 300 遍"和"12,000 轮不归还"两行，以及最初那次失败，是重启之前量的；那台机器的内核版本没有记下来，量到的表现和这条规则一致。其余各行和后面的变异是重启之后量的。

**实测**：

| 量了什么 | 结果 |
|---|---|

**改了什么**（`tests/test_eval_real.py`）：

- 断言从"峰值 ≥ 作业前内存"改成"作业前内存 − 峰值 ≤ `rss_accounting_slack_mb()` + 0.1"。
- `rss_accounting_slack_mb()` 是测试文件里新加的函数，按上面的规则，从本机的处理器数和页大小算：3 × 处理器数 × (max(32, 2 × 处理器数) − 1) 页。4 个处理器、4 KB 的页是 1.453 MB。
- 加的 0.1 MB 是两个数各自四舍五入到 0.1 MB 带来的（各 0.05）。
- 两个数都是 0.1 MB 的整数倍，所以在 4 个处理器的机器上：峰值比作业前内存低 1.5 MB 以内通过，低 1.6 MB 失败。
- 界线跟着处理器数走：2 个处理器 0.73 MB，4 个 1.45 MB，8 个 2.91 MB，16 个 5.81 MB，64 个 95.3 MB（在那样的机器上内核的出入真有这么大，这条断言也就弱得多）。开发机和 GitHub 上跑过的 runner 都是 4 个。
- 界线之外没有再加余量。理由：这个界线不是"见过的最大值再放大几倍"，而是内核规则的上限。上表里专门去凑，也只能正好凑到它，凑不出更多。普通情况下见过的最大值是它的 58 %（864 KB，多线程的探针）；真实测试里见过的是 0.4 MB。
- 函数的说明和断言上方的注释写了：两个数各是什么，为什么会差，见过差多少。

**放宽了什么**：改之前，评测工具报的峰值只要比作业前内存低，哪怕 0.1 MB，这个测试就失败；现在低 1.5 MB 以内不失败。也就是说，评测工具把峰值少报 1.5 MB 以内，这个测试看不到了。

### 3. 评测工具的两处重复

**（一）轮廓读取：比过了，两个函数不等价，没有合并。**

评测工具用自己的 `load_footprint` 读建筑的轮廓来打分，产品用 `crowd3d.scene_io.load_footprint_rings`。任务说明要求先证明两者等价再合并，有任何不同就不合并、把不同报出来。在改之前的代码上跑的结果：

- **提交在仓库里的轮廓**：目录的 13 个文件，三个测试集的 13 个文件（14 栋建筑的条目，合成集的两栋共用一个文件），一共 26 个文件。每个文件在三个不同的坐标原点下各读一次，78 次比较，两个函数返回的外环逐字节相同。这 26 个文件全都是单个 `Polygon`。
- **自己造的 29 种输入**：

| 结果 | 几种 | 哪些 |
|---|---|---|
| 两边返回同一个数组 | 8 | 单个 `Polygon`（裸几何、`Feature`、带内环、环没闭合、`FeatureCollection` 里两个多边形、Nominatim 的列表、只有两个点）；`Polygon` 在前、`MultiPolygon` 在后 |
| 两边报同一种错 | 10 | 不是 JSON、空文件、没有任何多边形、只有 `LineString`、坐标里有文字、点带高度、点只有一个数等 |
| 两边都报错，错的种类不同 | 3 | `Polygon` 没有 `coordinates`（评测 `KeyError`，产品 `ValueError`）、`coordinates` 是空列表（`IndexError` / `ValueError`）、是 `null`（`TypeError` / `ValueError`） |
| 只有产品读得出来 | 5 | 只有 `MultiPolygon`（评审说的那一种，2 例）；一个坏掉的 `Polygon` 后面跟着一个好的（2 例：评测在第一个上报错，产品跳过它）；`Polygon` 的环是空的（评测报"没有多边形"，产品返回一个空数组） |
| **两边都读得出来，结果不同** | 3 | ① `MultiPolygon` 在前、`Polygon` 在后：评测跳过 `MultiPolygon` 取后面那个 `Polygon`，产品取 `MultiPolygon` 里最大的一块。② 空环的 `Polygon` 后面跟着一个好的：评测取后面那个，产品返回空数组。③ 只有一个点的环：评测返回 0 个点，产品返回 1 个点 |

所以结论是：在今天所有的测试集和目录上两者完全一样，但它们不是同一个函数。尤其是 ① ——一个合法的 GeoJSON，两边悄悄读成两栋不同的东西——比评审报的"评测直接报错"更隐蔽。合并以后评测会跟着产品走，这多半是想要的，但它改的是评测工具对某些输入的行为，按任务说明留给负责人决定，这一步没有合并。

做了一件不改行为的事：加了一个测试（`tests/test_eval_real.py::test_the_harness_and_the_product_read_the_same_ring_from_every_committed_outline`），目录和每个测试集点到的每个轮廓文件，两个函数必须返回逐字节相同的外环；并把第一种分歧（只有 `MultiPolygon`：产品读得出，评测拒绝）写成断言。以后谁往目录里加一个两边读法不同的轮廓，这个测试先失败，不用等到基准跑到一半才崩。拿 4 种改坏的写法试过（评测取多边形的最后一个环、产品不去掉闭合点、产品把东和北写反、评测接受 `MultiPolygon`），都失败。

**（二）每次请求的文件数上限：合并了。**

`scripts/eval_real_landmark.py` 原来自己写了一行 `MAX_FILES_PER_UPLOAD = 50`，旁边的注释说"`crowd3d.api` 每次请求最多收这么多"，但没有任何东西保证两个数相等。现在这个名字直接从 `crowd3d.api` 导入，评测工具里不再有这个赋值。

- 两个数原来都是 50，所以 `plan_arrival` 切出来的请求和以前一样。
- 新测试（`tests/test_eval_real.py::test_a_session_is_split_at_the_limit_the_api_itself_enforces`）：评测的源码里不能再出现对这个名字的赋值；上限 + 1 张照片的一次到访切成"上限张、1 张"两个请求。评测自己再留一份（数值相同，或者改成 49）时它失败；把 API 的上限改成 20 时它照样通过，评测跟着变。
