# 测试

> "每一套测什么"以下的清单原来是 README 的"测试"一节，D34 C 部分第 2 步（2026-11-13）搬到这里，文字没有改（数量跟着这一步更新了）。"怎么跑"和"已知的缺口"是这一步新写的。

## 怎么跑

先按 [README](../README.md) 的"快速开始"装好环境（`pip install -r requirements-dev.txt -c requirements-lock.txt`）。下面的命令都在仓库根目录执行。

| 要跑什么 | 命令 | 要多久（4 核的开发机） |
|---|---|---|
| 快速测试，单进程。结果以这个写法为准 | `python -m pytest -q -m "not slow"` | 约 5–6.5 分钟 |
| 快速测试，分 4 个进程 | `python -m pytest -q -m "not slow" -n 4` | 约 1.5–2 分钟 |
| 慢测试：真实 COLMAP、端到端验收、风格化作业端到端、13 个地标的素模回归 | `python -m pytest -q -m slow` | 约 8–10 分钟。不要加 `-n`：机器上同时只能有一个 COLMAP |
| 网页的 node 测试（要 Node ≥ 22） | `node --test 'web/tests/*.test.mjs'` | 约 2 秒 |
| 代码检查，规则在 `pyproject.toml` | `python -m ruff check .` | 不到 1 秒 |
| 文档里由代码生成的表有没有跟上代码 | `python scripts/gen_docs.py --check` | 约 3 秒 |

时间有两个数的，是两台开发机（Xeon 2.3 GHz 和 2.10 GHz）上各量的。

只想跑一部分测试时用标记：`-m "not slow and not structure"` 去掉素模那一族（占快速测试约三分之二的时间），`-m structure`、`-m harness`（`scripts/` 的测试）只跑那一族。直接运行 `pytest` 和 `python -m pytest` 效果相同。

另外几点：

- `pytest` 找得到 `crowd3d`，靠的是 `pyproject.toml` 里的 `pythonpath = ["."]`：包没有安装（也装不了，见 [CONFIG.md](CONFIG.md#服务要在仓库的检出目录里运行)）。D34 C 部分第 1 步之前没有这一行，直接运行 `pytest` 会报 `ModuleNotFoundError: No module named 'crowd3d'`，只有 `python -m pytest` 能用。测 `scripts/` 的测试自己按文件路径加载脚本，不靠这一行。
- 标记要先在 `pyproject.toml` 里登记，没登记的标记是错误（`--strict-markers`），不会悄悄选不中任何测试。`-n` 没有写进默认选项，要并行就自己加。
- node 测试也在快速测试里：`tests/test_web.py` 调 `node --test`。机器上没有 `node` 时这个测试是跳过，不是失败。
- **CI**（`.github/workflows/ci.yml`）：每次 push 和 pull request 跑 `fast` 作业，依次是代码检查、快速测试（`-n auto`，每个处理器一个进程）、node 测试；测试两步在前面的步骤失败时也照跑。`slow` 作业跑慢测试，只在手动触发和每周一 03:17 UTC 跑。GitHub 只从默认分支跑这两种触发，而工作流还在功能分支上，所以 `slow` 作业到现在一次都没有在 GitHub 上跑过。
- 怎么改测试的工具配置（依赖文件、标记、并行、ruff 的规则）和它们的来由，记在 [decisions/D34-part-c-engineering.md](decisions/D34-part-c-engineering.md) 第 1 步。

## 每一套测什么

分四层：合成数据上的自动化测试（每张照片的真实位姿都已知）、真实 COLMAP 的端到端验收、Web 的 node 测试，以及在冻结测试集上跑的基准（含 10 栋著名建筑的真实照片）。

### 快速测试

- `python -m pytest -q -m "not slow"`：1436 个快速测试，都不需要真实照片（加 `-n 4` 分 4 个进程跑）。覆盖范围：
  - 点云链路：地理计算、EXIF、校验、规划、存储、作业（含风格化作业和替换规则）、上传、API、发布质量门（`qa.py`）、合成数据。
  - D30 第一步（`test_api.py`）：任何不需要登录的 GET（含失败作业的错误信息）都不给出照片的库内 id、服务器路径、照片的 GPS 经纬度、方位和距离、朝向、上传时间或相机的位姿（精确到 0.1 m，或整米并排写出），上传者只出现在共同完成者列表里；扫描的是整段响应文本，字符串里的数字也算；`/files/models` 只提供 `.ply` 和 `.glb`。
  - D30 第二步，同意和撤回（`test_api.py`、`test_store.py`、`test_ingest.py`；D32 把"上传时可选的同意"换成了必须同意的用户协议，见下面 D32 那条）：没通过的照片不记同意、不给凭证；撤回凭证只对自己那张照片有效，撤回后同意清空；公开 id 的密钥文件 `<data_dir>/public_id.salt` 权限 0600、重启不变、换数据目录就不同、任何地址都取不到，数据目录放进网页目录时服务拒绝启动；密钥和数据库绑定：还有照片公开着位置时，换了环境变量里的密钥、删掉或换掉密钥文件，服务都拒绝启动，也不另生成密钥，换回原来的密钥后旧凭证照样能撤回；没有照片公开时改用新密钥并记警告；`forget-lost-salt` 在没有数据库、服务正在运行或密钥没变时拒绝执行，执行后所有照片都不再公开、照片文件保留；共同完成者只给昵称、按昵称排序；基准上传时每张照片都同意协议（`test_eval_real.py`；D33 起每个伪用户登记时同意一次）。

  - D30 第四步，公开的拍摄位置接口（`test_api.py`、`test_photoposes.py`、`test_jobs.py`、`test_structure_pipeline.py`）：`/poses` 只列同意公开、通过的照片，每行正好等于它内部位姿的公开行，`id` 等于上传时给的 `public_id`；撤回的、库里同意版本不认识的都不列，没通过的照片没有 `public_id`；列表是最近一次重建作业结束时的快照，只有上传不会变，撤回马上生效；风格化作业记下的吸附（或旧记录旁边 `.style.json` 里的）接受了才移动相机，也让没定准的模型的相机能显示，拒绝的吸附、没有 GLB 的模型都不算；任何辅助函数都不把拒绝的吸附当作定住了坐标系；`uncertainty` 引用测试集上实测的比例，带最低和最高的一栋一次，EXIF 标明是样本内；任何人都能让快照提前更新（匿名手动重建，或者别人自己上传几张照片让作业开始），新出现的那一行就是新昵称的（协议和上传说明写明了这一点）。泄漏扫描也扫 `/poses`（行之外的部分和其他接口一样扫，没同意的相机不出现在任何一行的 1 米内）和服务提供的点云文件。
  - D30 第五步，视觉定位的记录（`test_store.py`、`test_jobs.py`、`test_photoposes.py`）：`localizations` 表每张照片一行，JSON 位姿原样存取，再写一次就整行替换，按地标取；只给通过且同意公开位置的照片写（没同意、没通过、同意版本不认识、地标不对、照片不存在都不写），撤回同意或清掉全部同意时定位结果一并删除，之后也写不进去；老数据库打开时自动建表；`JOB_LOCALIZE` 和风格化一样排在重建作业之后、不重新规划、不重建（视觉定位关着时，留下的定位作业什么也不做就结束）；存储的 `LocRecord` 给出的位姿和它的 JSON 形式一样。
  - D30 第六步，视觉定位的纯函数部分（`test_localize.py`）：只试同意公开、通过、有 EXIF 35 mm 焦距和处理图、没有显示中的 SfM 相机的照片（没同意的、同意版本不认识的、没通过的不试也不留记录；相机被标记的、注册在候选地图里的、没有焦距的、没有处理图的、地标没有候选地图的各记原因；坐标系没定准的模型里扣下的相机照常去试；候选地图没变就不重试）；候选地图只取每个目标最新的已发布模型，要坐标系定准（吸附被接受也算，拒绝的不算）、有地理锚点、特征版本一致；`maps_key` 和顺序无关，规则版本变了就重试；配对是候选地图里每张不同的照片（不和自己配），超过上限按离 GPS 的远近取；每道门槛（对应数、内点数、内点率、重投影、对称歧义的次优位姿比、焦距核对差 20%、焦距比 0.3–8、半径、高度、光轴偏离）在门槛上通过、刚过门槛就拦下，变异检查 38 个都拦住；主解必须用 EXIF 焦距，自由焦距的解只作核对、永远不当位姿，核对没解出来也不给位姿；次优位姿按米（乘锚点尺度）和度判断是不是另一个位姿；跨模型取内点最多的、同数时全景优先，另一个接受的模型内点过半而朝向差超过 25° 时判歧义；位姿经模型的地理锚点转 ENU，和模型自己的相机一致（俯仰、横滚也一致），地图图像对不上模型相机时整张地图不用；离自己 GPS 太远只记成冲突、不拦（参数打开才拦）；记录里的位姿正好是 photoposes 要的键，photoposes 给出 loc 位姿、误差范围是模型的 sfm 范围和 1.5 m / 0.7° 按平方和合成。
  - D30 第七步，视觉定位的 COLMAP 部分（`test_localize.py`，在编出来的数据上直接跑 pycolmap）：2D-3D 对应按"查询关键点 + 三维点"去重，地图关键点没有三维点或越界的不算；焦距固定时解出来的焦距就是给的值、离群点不进内点，自由焦距能估出真值；位姿经地理锚点转 ENU 后和真值一致；EXIF 焦距是实际的 1.5 倍（裁剪过的照片）时焦距核对拦下；另一个面的对应占两成时次优位姿检查拦下；对应不够 30 个时一次也不解；`read_two_view_geometry` 按要的顺序给出匹配；特征缓存里按另一个顺序存的图像对也能写进来，收获时每个图像对按它当初算的顺序存；处理图不见了、没有地图、地图照片的处理图全不见了、要求停下或过了截止时间时不动 COLMAP；COLMAP 读不了的查询、一个特征都没有的查询、地图照片全读不了的查询都记为跳过（不算定位失败），不出错；没存下的地图不读，读不了的地图让查询记为没有地图，记录仍按候选地图的 `maps_key` 存，下一个作业不再试（按读进来的地图存就会每次重试），`maps_key` 不收读进来的地图；假重建器没有定位器。

  - D30 第九步，视觉定位的基准（`test_eval_real.py`、`test_benchmark.py`）：给了定位记录时，接受的按来源 `loc` 打分，汇总多一个 `loc` 块：记录按状态和原因、显示出的定位位姿的对错（离自己 GPS 太远的那些单独再数一遍）、每张定位出的照片原来显示什么和前后的对错、试过的照片按类别、每张地图上的对错和地图自己相机的误差（定位器自己的计数不会盖掉这张表，重名就报错），只有计数和模型 id；补算的定位用的吸附就是打分用的那些（给了重新风格化就用它的，否则用运行自己的）：吸附被接受的未定准地图成为候选地图，它的相机算显示中，照片不试也不留记录；`photo_pose_loc_wrong` 数定位出的错位姿；通过标准 `d30-v1`：两条零门槛（定位错、看错面）在一栋的一次重复上违反就不过，没有参考位姿的建筑（悉尼歌剧院）点名留出、有参考却没有值的仍是 INSUFFICIENT，写错的零门槛读不进来；错误比例的守卫逐栋看，定位 CPU 超过运行 CPU 的四分之一就不过，提高和覆盖只报告（比例的报告行带 B 的个数和 Wilson 区间）。

    - 凭证是 64 位十六进制，100 次登记 100 个不同的凭证；数据库文件和 WAL 里只有哈希，没有凭证；格式不对、不认识的凭证认证不过；
    - 登记先查协议版本（`terms_required` / `terms_outdated`）再查昵称（去掉首尾空白，任何文字，1–64 个字符，不含控制字符和落单的代理项，含代理项时 422 不回显、不 500），不合格时一行都不存；201 的响应正好是昵称、版本和凭证，`Cache-Control: no-store`；`GET /api/contributors` 是 404；

## 已知的缺口

测试没有守住的地方，都是已经知道、还没做的：

- **慢测试的 CI 作业没有在 GitHub 上跑过**（见上）。慢测试只在开发机上跑。
- **锁文件里的间接依赖没有测试守着**：`tests/test_tooling.py` 核对的是直接导入的包钉的版本；间接依赖漂了或者缺了，没有测试会失败。
- **还有 7 个时间上限写成秒**。另外 10 个已经改成随机器快慢伸缩的单位；这 7 个在两台开发机上都过，换一台慢得多的机器可能不过。
- **`tests/test_web.py` 在没有 Node 时跳过**，Node 太旧时 node 测试自己会报错；`test_code_fingerprint_covers_the_code_a_run_executes` 在不是 git 检出的目录里会失败。
- **测试文件互相导入来共享场景**（评审时数的是 14 个文件、33 条导入），没有整理成公共的夹具模块。
- **演示脚本的测试算在慢测试里**：它用的是假重建器，只是因为写在 `tests/test_e2e.py` 这个整体标成慢的模块里。
- **D25-T（倾斜）只有单元测试**：仓库里没有入口调用它，也就没有端到端的测试（[STATUS.md](STATUS.md)）。
- **几处吸附门检查没有回归测试**；真实模型没有一个走到门的"通过"分支（[STATUS.md](STATUS.md)）。
- **快速测试看不出"峰值内存在作业开始之前就读了"这种错**：假重建器的作业不占内存，只有慢测试看得出（[decisions/D34-part-c-engineering.md](decisions/D34-part-c-engineering.md) 第 1 步第 8 小节）。
- **基准不在 pytest 里**，通过标准里有几项要人读运行产物来判（[BENCHMARK.md](BENCHMARK.md) 6.11、6.12 节）。
- **没有类型检查，也没有跑过格式化工具**。
- **文档的测试只管得到一部分**（`tests/test_docs.py`）：链接只查仓库内的，不查外部网址；[API.md](API.md) 只比方法和路径，"说明"里写的请求、响应和上限是手写的，没有和代码对；[CONFIG.md](CONFIG.md) 和代码地图里手写的"含义""职责"只查有没有写，不查写得对不对。
