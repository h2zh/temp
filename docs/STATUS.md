# 现状、局限和下一步

> 原来是 README 开头的"现状"一段和最后的"原型的局限""下一步"两节，D34 C 部分第 2 步（2026-11-13）搬到这里。文字没有改，只把"见上面某一节"换成了链接，并加了三处注（都标着"D34 C 部分注"）：两处标明数字来自不在仓库里的驱动脚本，一处指出一句话已经过时；"原型的局限"最后加了两条评审留下的工程缺口。一屏的摘要在 [README](../README.md) 的"现状"一节，数字的出处在 [BENCHMARK.md](BENCHMARK.md)。

## 现状

> **现状**：上传、校验、重建、发布这条链路已经接进服务和网页。结构优先也接进了作业系统：有 OSM 分件快照的地标，每个发布的模型会自动生成一个 GLB，地标页链到它。但今天每个真实众包模型都过不了配准门，产品又只用一种可商用的天空掩码，所以产品给出的都是 OSM 分件的素模，没有照片量出的数字（模型本来就不上色，D29）。详见"原型的局限"。D30（2026-11-04）：别人看到的照片拍摄位置取整到 1 米、1°，不带昵称；视觉定位做好了，但测试集上代价超标，默认关，见 [D30 的记录](decisions/D30-photo-poses.md)。D32（2026-11-05）：上传必须同意用户协议（草案，待法律审核），通过的照片确定了位置和朝向后，连同取整后的拍摄位置公开，上传者可以撤回；"从这张照片的角度看"把照片和素模放在一起对照；每个页面都能切换浅色 / 深色和中文 / English，默认跟随系统，见 [D32 的记录](decisions/D32-terms-compare-appearance.md)。D33（2026-11-05）：用户协议改在登记时同意一次（昵称加同意协议，上传带登记时拿到的凭证），上传时不再勾选；视角取整到 1°，见 [D33 的记录](decisions/D33-registration-fov.md)。D31（2026-11-03）加了照片资格和立面按注册张数过门，全新运行按事先写好的标准是 FAIL，见 [D31 的记录](decisions/D31-photo-eligibility.md)。

## 原型的局限

- **真实照片只测了十栋建筑，阈值是样本内的。** 发布质量门、风格化配准门、#73 的开关和锚点下限都是在开发集（核心五栋、合成集、mdx-two-v1）上定的；D31 的占比 1/3、按张数的 6 张和印度门参考的修正，还看了留出五栋上 F 的运行。留出五栋先只用冻结的提交跑过 B0 和 F，F 有三栋（林肯纪念堂、印度门、悉尼歌剧院）一个模型都不发布，所以那时留出集上的通过标准和标定都是"证据不足"（[docs/REVIEW_ADOPTION.md](REVIEW_ADOPTION.md)）。D31 的全新运行在这五栋上只是复现测量：林肯纪念堂、印度门有了模型，悉尼歌剧院仍然没有。
- **按张数发布的立面，墙可能偏离轮廓（D31）。** 质量门没有一项拿墙和 OSM 轮廓比。D31 全新运行里，圣家堂新显示的南面、西南面两个按张数过门的立面，位姿对，墙却大段不在轮廓 1.5 m 内（地理坐标里超出 5 m），test 上的两条覆盖守卫因此不过；林肯纪念堂的两个张数模型，自己的相机只对 19 / 39。
- **公开的拍摄位置，范围诚实但宽（D30）。** 显示的位姿约三分之一离参考超过 10 米或 15°，86–88% 落在自己标出的 2σ 范围里。手机 GPS + 罗盘那一行在留出集上 14 张有参考的只有 1 张在 10 米 / 15° 内。同意公开的照片里，dev 每次运行约 3/10、test 约一半只有 GPS、没有可用的罗盘，不显示。视觉定位能多放准的很少（约 1%），代价又超标，默认关。
- **模型没有颜色（D29，2026-11-03）。** 产品负责人决定放弃给模型上照片颜色，上色代码已删：GLB 里没有贴图，每个面都是素模，地标页的标签都是"素模（…）"。靠颜色才认得出的地标（洗礼堂的黑白条纹）只剩形状。照片拍到哪些墙只用于 D24 和结构指标，屋顶从不算拍到。
- **真实众包模型用不上照片证据。** 配准门要求相机位置误差 ≤ 1.5 m；拍摄者离墙 40–90 m 时，只靠 OSM 轮廓和手机 GPS 证明不了这么准，所以真实建筑的模型一个都过不了门，D15、D24 用不上这些照片（D29 前：一面墙都不上色）。八边形这类轮廓（洗礼堂）在锚点的偏航 σ 下，窗口会被对称周期截短，众包模型的吸附都会被拒。要让照片证据进来，需要不靠轮廓的偏航和尺度来源（[docs/VISUAL_LOCALIZATION.md](VISUAL_LOCALIZATION.md) 的视觉定位；D30 只实现了给照片定位、只用于显示的那一小块，不给模型提供偏航和尺度），或者产品决定放宽标准。
- **模型在地图上的位置不确定度现在报出来了，而且很宽。** API 的 `geo` 块给出每个分量的 σ。尺度 σ 的中位数约 ±43%；在核心五栋上，点中位处的水平 σ 中位数是 16.9 m（7.7–47.1 m），大部分来自尺度。F 在留出集上标定证据不足，匈牙利国会大厦的水平 σ 还说小了（6 个模型里 4 个在 3σ 外）。D31 的全新运行在留出集上有 22 个可核对的模型：四个分量的 2σ 覆盖都过，3σ 外的比例只有水平位置不过（1.5 / 22，全是匈牙利国会大厦西面）。所以地标页的"位置 ±X 米（1σ）"仍然关着。锚点也没让位置变准：地理相机误差的中位数 dev 6.58 m、test 15.07 m，评审之前是 5.99 m、15.78 m。
- **配准门的已知漏洞（任务 #73）已经修了，但"0 个错误通过"仍只对已记录的运行和对抗用例成立。**
  - 现在门读锚点的偏航 σ；窗口被对称周期截短、或者模型没报偏航 σ 时拒绝；吸附后相机离自己 EXIF GPS 的中位距离太远（> max(20 m, 3 × 锚点的水平 σ)）时拒绝。对抗用例里错误通过从 69 个降到 0 个。代价是精确别名那组里本来对的 78 个通过只剩 16 个。
  - `scripts/stylize_model.py --snap-from` 复用旧吸附前，流水线模型要先按现在的门重新核对。
  - 几处吸附门检查（决定能不能用照片证据）还没有回归测试。真实模型没有一个走到门的"通过"分支，所以开关的好处在真实数据上看不出来。

  D25 也依赖这一点：近圆形的轮廓（洗礼堂有 23 个对称别名）上，纠正要在所有别名转角下都成立才采用。
- **框架几乎全部来自 OSM，照片的贡献很小。** 结构优先让模型认得出来了，例如亚琛的分件、穹顶和尖顶，但形状主要是 OSM 志愿者画的。照片的贡献：
  - 洗礼堂：打开 D24 以后，85 个数字里有 36 个来自照片，大多是立面凹凸。
  - 亚琛：D24 的尺度条件不满足，没有打开；D25 只纠正了一处，唱诗堂顶高"至少 36.26 m"（OSM 写 32 m），照片数字从 0% 升到 0.21%。
  - 比萨：D25-T 只在参考模型上通过，量出倾斜 4.59°，朝 177.0°（公开值约 3.97°）。已发布的众包模型都不带倾斜：它们只拍到塔的一面，点云轴不够准。（D34 C 部分注：这组数是一个不在仓库里的驱动脚本 `pisa_tilt.py` 量的；仓库里没有任何入口调用 D25-T 的代码，只有单元测试调，所以它从仓库复现不了，见 [数字出处](decisions/README.md#数字出处和-scratch-路径)。）
  - 洗礼堂上 D25 没有改任何值。
  - 以上数字都来自参考场景（全部照片、已知位姿），而且另用了研究用的第二种天空掩码 Dm+R。只用产品的 A+R 时，洗礼堂和亚琛的参考场景上照片数字都是 0，D25 不跑。众包等级上的 D25-H 和 D25-B 本来也关着。（D34 C 部分注：跑出这些数的参考重跑脚本和 Dm+R 掩码都不在仓库里，见 [数字出处](decisions/README.md#数字出处和-scratch-路径)。）

  OSM 没画分件的建筑，只能把外轮廓拉伸成体块；标签缺了的地方，用约定比例或 3 m 的"高度待定"矮台代替。只在 Wikidata 有条目、地图上没有轮廓的地标还不支持。
- **结构优先接进了产品，但只给出 OSM 分件的素模。**
  - 产品给的：有分件快照的地标（目录里 13 个），每个发布的 COLMAP 模型一个 GLB，带 OSM 分件的体块、屋顶原语和来源，标"素模（照片未对齐）"。风格化作业的子进程 CPU 中位数 4.9 s、最多 19.7 s，峰值内存不超过 300 MB（核心五栋的 20 个模型）。
  - 产品不给的：照片量出的数字（照片颜色 D29 起本来就不给）。原因有两个：每个真实众包模型都过不了配准门，判定器不跑；只有一种可商用的天空掩码，按"两种掩码"的规则，D25 不跑，天空轮廓线一路不起作用。
  - 没有分件快照的地标不出 GLB。
  - 没有"重新风格化"的入口：这个功能上线以前发布的模型，以及分件快照或风格化代码改了以后的模型，要等下一次发布才有新的 GLB。
- **D24 和 D25 按放宽后的标准运行（D26，2026-10-28）。** 对抗加固做了五轮也没有收敛，产品负责人决定放宽标准：
  - 只为合成攻击场景或伪造记录加的守卫都删掉了，D25 也不再往下改高度。真实数据的结果和清理前逐项相同，发布出去的 GLB 二进制部分逐字节相同。
  - 已知能骗过 D25 的合成情形：树冠盖满平顶、脚手架网围住"高度待定"矮台、网加临时顶棚的整体围护。它们会发布比真值高的值或下界。完整列表见 [docs/STRUCTURE_FIRST.md](STRUCTURE_FIRST.md) §2.4.8 第十五部分。
  - 发布检查不防伪造记录。
  - D15 改高度现在要读到这块积木自己的屋顶（D27，2026-10-28）。合成场景里，离墙很近的脚手架网顶、女儿墙不再被当成檐口采用；代价是屋顶从地面看不见的平顶分件，以及小于约 8 m × 8 m 的分件（除非三维直线量到屋脊或顶点），D15 不再改。树冠盖在屋顶上时，树冠上的点能拟合出一个"屋面"，D15 仍可能采用树冠的高度。
- **全景模型在真实建筑上一次都没发布过**，每栋却要花 15–24 分钟反复尝试。不设上限跑完的勃兰登堡门和圣母教堂也没发布。游客只拍"好看的那一面"，很多方向几乎没有照片。（D34 C 部分注：这句话写得早。按仓库里的结果文件，D31 的那次 dev 运行在比萨斜塔上两次重复里有一次发布了全景模型（`eval/results/commons-ten-v1/d31-dev.json`，[BENCHMARK.md](BENCHMARK.md) 6.14 节的表）；D34 的两次全新运行里十栋都没有。）
- **采集端**：
  - 只收相机原图：没有 EXIF 判 `no_exif`，EXIF 里没有 GPS 判 `no_gps`。截图、修图软件或聊天软件转存的副本，通常两样都没有。
  - 手机浏览器从相册选图时，可能会去掉 GPS，Android 上很常见。Commons 上也只有约 1/7 的照片带 GPS。
  - 不支持 HEIC，因为没有安装 HEIF 插件。
  - 磁北朝向只给出警告，没有做磁偏角修正。D34 起地理配准和质量门不用磁北和没写参照的朝向；上传时仍然用它查是否背对建筑（拒绝码 `facing_away`）。改成只警告的开关（`facing_away_warns_other_refs`）做了，用全新的重建量过，没有通过事先写下的守卫，保持关（D34 第 7 步）。
- **几何**：
  - 重力方向的估计假设手机竖直拿、地面大致水平，单个立面可能残留几度的倾斜。勃兰登堡门的模型相对参考的中位倾斜是 3.4°，原因没查清。
  - 无法地理配准时，回退方案的尺度比较粗略。
  - 重建只输出稀疏点云，没有稠密重建和 3DGS。[docs/PHOTOREAL_LOCAL.md](PHOTOREAL_LOCAL.md) 说明怎样导出数据，在本地用 GPU 训练 3DGS。
- **重建**：只用 CPU，单线程串行。特征和匹配现在有地标级缓存，但建图每次仍从零开始，没有增量注册：续建做了，可是开发集验证没过（版本连续性 56%，要求 90%；先试续建再从零重建，净省的 CPU 为零），默认关。用缓存时，不设上限跑完勃兰登堡门（150 张照片）要 1,345 s 墙钟，圣母教堂（111 张）要 3,953 s。
- **服务**：单机 SQLite 加本地文件，一个数据目录只能由一个服务进程使用。没有账号和内容审核。上传要先登记（D33）：只有昵称加同意用户协议，没有密码和邮箱，昵称可以重名；登记的凭证存在浏览器的 localStorage 里，库里只存它的哈希；还没有办法吊销被盗的凭证，也不能在服务器上删除登记或改昵称（[D33 的记录](decisions/D33-registration-fov.md)）。别的写操作（建地标、手动重建）仍不用认证。登记和上传都没有限流。登记的凭证只放在 POST 请求体里，不进地址、请求头和日志，422 也不回显它（[D33 的记录](decisions/D33-registration-fov.md)）。撤回靠这台设备：登记还在，就能向服务器查回用它上传的照片并撤回（D34 第 2 步）；清空了浏览器存储或换了设备，登记本身就没了，只能联系运营方，而运维还没有下架命令；这个查询接口不分页。上传的单次请求最多 50 × 25 MB，别的请求最多 64 KiB，超出时在写盘和解析前返回 413（D34；回答开始之后才超限的请求体不是 413，读了就丢，见 [API.md](API.md)）。上传表单的文本字段最多 8 个、每个 4 KiB（D34）。同时让 Pillow 处理的上传最多 2 个（`max_concurrent_decodes`，读文件头和解码都算）；贴着像素上限的 WebP 一次解码仍要约 0.9 GB 内存，所以解码最多占约 1.6 GB（实测；靠服务启动时管住 glibc 的分配器，别的 C 库上没有这个保证）。排队的上传各自拿着自己的文件，最多 40 个 × 25 MiB，约 1 GB；限制同时处理的上传个数是上线前事项。EXIF 由自己的读取器读，工作量有上限；文件头超过上限的图在 Pillow 打开之前就拒绝，上限以内最贵的文件头（一个 24 MB 的 PNG 文本块）实测 0.16 秒、多占 114 MB（D34）。模型点云、风格化 GLB、每张通过、没撤回、确定了位置和朝向的照片（去掉元数据、缩小）和它取整后的位姿（D30、D32、D33）对所有人公开；撤回的和没通过的照片什么都不公开。公开位姿的快照可以被任何人用手动重建或几张上传提前更新，上传的人少时公开的行可能和新出现的昵称对上（[D30 的记录](decisions/D30-photo-poses.md)）。照片接口每次请求都重新编码（中位约 105 ms），没有限流；运维还没有下架某张照片的命令，只有上传者能凭撤回凭证撤回。用户协议是草案，等法律审核；D32 的一次性迁移上线前要删掉（[D32 的记录](decisions/D32-terms-compare-appearance.md)）。进程崩溃中断的作业最多重跑 1 次，同一个作业被中断 2 次（`max_job_attempts`）后判为失败。`work/` 目录在作业结束后自动清理（`keep_work_dirs` 或环境变量 `CROWD3D_KEEP_WORK_DIRS=1` 可保留）；风格化作业失败时，原因先存到模型旁边再清理（D34，见 [CONFIG.md 的"数据目录"](CONFIG.md#数据目录)）。`maps/` 下的特征缓存不淘汰，每张照片约 1.1–1.7 MB。
- **基准**：`scripts/benchmark.py` 的默认数据目录写死成开发机上的一个临时目录，在别的机器上要设 `CROWD3D_TESTSET_ROOT`、`CROWD3D_BENCH_DIR` 或每次传参数；新重建器要改代码注册；风格化的参数还不能通过配置调；逐照片指标还不按"没见过的摄影师"分开报。
- **网页**：地图底图依赖 OSM 公共瓦片（Leaflet 和 three.js 由服务自己提供，不再依赖 CDN，D34）；网页文件和模型文件用 gzip 压缩着发（D34 第 4 步；`three.module.js` 每个新访客传 0.26 MB），没有 brotli，API 的 JSON 不压缩，页面的 `import` 仍是一个接一个发的；内容安全策略只在 Chromium 里实测过，而且拦不住页面跳转（见 [docs/decisions/D34-review-fixes.md](decisions/D34-review-fixes.md) 第 3 步）。地标页点云上画的是全部公开的拍摄位置，不按立面分开；风格化模型吸附过的，点云上不画（点云没有跟着吸附移动），改为提示去风格化模型里看。
  - 只有中文和英文（D32）。
  - "公开的拍摄位置"表在卡片窄于 640 px 时（手机，或 700–1024 px 宽时的主栏）每行竖排、值前写列名，不用横着滚动；360 px 的滚动框有边框，底边的渐隐标出被截断的一行（D33；D32 时手机上要横着滚动才看得到朝向和 ±范围）。不支持 CSS 容器查询的旧浏览器还是表格，要横着滚动。卡片宽 640 px 以上时还是表格，滚动框也有边框和底边的渐隐，框高 376 px，被截断的那一行透过渐隐看得见（D33）。
  - 风格化查看器的语言和外观切换在面板里：模型加载中、加载失败和 `ui=0` 时没有切换（选择和别的页面共用）。
- **D25-T（倾斜）没有入口**（评审"工程做法"的一条，D34 C 部分只做了标注，还开着）：`crowd3d/tilt.py` 和 `correct.py` 里的 `rule_t`、`tilt_consensus`、`apply_tilt`（评审数的是约 650 行）产品和脚本都不调用，只有单元测试让它们保持通过。量出比萨倾斜的驱动脚本 `pisa_tilt.py` 和它用的三个读取模块只在 `<scratch>` 里，没有进仓库（[数字出处](decisions/README.md#数字出处和-scratch-路径)）。两条路：把驱动整理后提交、配一个合成斜塔的端到端测试；或者明确把这部分标成研究代码。
- **服务只能在仓库的检出目录里运行**（同上，还开着）：包不能安装，网页和默认的地标目录都取自检出目录，目录里的文件路径按"目录文件的上两级"解析。细节和摆错时的表现见 [CONFIG.md](CONFIG.md#服务要在仓库的检出目录里运行)。

1. **视觉定位**（[docs/VISUAL_LOCALIZATION.md](VISUAL_LOCALIZATION.md)；D30 只做了给同意公开的照片定位、只用于显示的那一块，默认关，§10）：新照片对已配准的地标级模型做绝对定位，让没有 GPS 的照片加入模型，同时提供不依赖轮廓的偏航和尺度。D30 测出的第一个障碍是代价：每张查询要和地图里每张照片匹配，大多数最后配不上，先要做检索。这是唯一能改变绝对位置和配准门结果的路，也是照片证据（D15、D24、D25）进入真实众包模型的前提。底子已经有了：每个已发布模型的稀疏地图存在 `data/maps/<地标>/models/` 下，锚点是独立的记录。
2. **单掩码的决定（D28）**：要么保留"两种掩码"的规则（现在的默认），要么让 A+R 单独算一路、门槛更严，后者要有自己的一轮验证。先要一个研究开关，把 A+R 自己的读数报出来才能权衡。另一条路是查清 Dm+R 或 C+R 的许可，得到第二种可商用的掩码。
3. **续建要一个更好的接受规则**：例如只在照片数超过 30 张时续建（小照片集保留三个种子的多样性），接受续建的门槛不用 `suspicious()` 的 5%，再定完整模型的重试规则（[docs/BENCHMARK.md](BENCHMARK.md) 6.8 节末尾）。改完要重新过开发集验证。
4. **评审里需要 GPU 的阶段**：GPU 特征和匹配（如 ALIKED + LightGlue）、稠密重建或 3D Gaussian Splatting。这台机器只有 4 核 CPU，验证不了；到有 GPU 的机器上时，同一个划分和 `review-v1` 可以直接拿来比。
5. **留出证据太少**：F 在五栋里有三栋一个模型都不发布；D31 之后只有悉尼歌剧院没有模型，但可核对的模型够 3 个的也只有圣家堂、印度门两栋，仍凑不出标定要求的"至少 3 栋、每栋至少 3 个模型"，而且这五栋对 D31 已经"烧掉"了。要加建筑，发一个新的测试集或划分版本，并用真实建筑做一次小规模实地采集，重新校准阈值，包括 GPS σ、模糊度和重复判定。
6. **引导拍摄**（方向 B）：采集端改为页面内拍摄，同时记录 GPS 精度、指南针和重力方向（DeviceOrientation），提示"还缺哪几面、哪几块积木还没被拍到"。
   - 这样可以绕开相册丢失 GPS 的问题，提高重力和朝向的先验。
   - 照片能给框架提供的证据也会更多。
